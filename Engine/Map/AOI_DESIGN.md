# 관심영역(AoI) 동기화 설계

## 1. 왜 필요한가

지금은 맵의 **모든 액터**를 **모든 플레이어**에게 매 틱 보낸다
([`Map::SyncActorState`](Map.cpp) 이 변경된 액터를 전부 직렬화하고 `SendWorldState` 가 브로드캐스트).

- 40,000마리 맵에 플레이어 50명이면, 한 명당 매 틱 40,000개 액터 정보가 나간다.
  10Hz · ActorInfo 약 30바이트 기준 **초당 수백 MB** 규모다.
- 클라이언트도 보이지도 않는 액터를 전부 생성/갱신한다.

CPU 는 부수적이다. 오히려 플레이어별로 메시지를 나눠 만들면 **직렬화가 중복**돼 CPU 는 늘 수도 있다.
**이 작업의 목적은 대역폭과 클라이언트 부하**이고, 성능 수치는 그 다음이다.

## 2. 지금 구조에 그냥 필터를 끼우면 깨지는 것

| 문제 | 원인 | 결과 |
|---|---|---|
| 유령 액터 | 액터 제거는 상태 갱신(`AIState_Destroyed`)으로만 전달된다 | AoI 밖에서 죽은 몬스터가 클라에 영원히 남는다 |
| 안 보이는 액터 | 정지한 액터는 `changeFlag` 가 없어 전송 대상이 아니다 | 플레이어가 새 지역에 들어가도 가만히 있는 액터는 안 보인다 |
| 입장 동기화 | `SendStateTo` 가 맵 전체를 보낸다 | 입장 순간만 전부 받고 이후엔 일부만 받아 상태가 어긋난다 |

그래서 필터 한 줄이 아니라 **enter / stay / leave 3-상태 프로토콜**이 필요하다.

## 3. 설계

### 3-1. 서버가 유지하는 상태

플레이어마다 "지금 보고 있는 액터 집합"을 서버가 들고 있는다.

```
Player 또는 Map 이 소유: std::unordered_set<int> visibleActors_;  // actorId
```

### 3-2. 매 틱 절차 (플레이어 단위)

```
A    = AoI 반경 안의 액터 집합           (그리드 쿼리)
enter = A - visible                     → 전체 스냅샷(GameObjectChangeType::All)
stay  = A ∩ visible, 이번 틱 변경분      → 변경 플래그만
leave = visible - A                     → 제거 통보(actorId 목록)
visible = A
```

- **enter**: 클라가 액터를 새로 만들 수 있도록 위치·타입·상태·체력을 모두 채운다.
- **stay**: 지금과 동일(변경 플래그 기반 부분 갱신).
- **leave**: 사망이 아니라 "시야에서 사라짐"이다. 클라는 사망 연출 없이 조용히 제거해야 한다.
- 액터가 실제로 제거될 때(`OnRemoveAgent`)는 **visible 에 들어 있는 모든 플레이어에게** leave 를 보낸다.

### 3-3. 입장/이동

- `Map::join` → `SendStateTo` 를 AoI 반경으로 제한하고 `visible` 을 그 집합으로 초기화한다.
- 게이트 이동은 캐릭터가 재생성되므로 `visible` 을 비우고 다시 시작한다.

### 3-4. AoI 반경

- 클라이언트 가시 거리와 맞춰야 한다(현재 몬스터 탐지 반경은 10, 그리드 셀은 2).
- **맵마다 다르다** — 좁은 던전과 넓은 필드가 같을 이유가 없다.
- 권장: `Map.json` 에 `aoi_radius` 추가, 미지정 시 기본값(예: 40). 데이터 추가이므로 GameDataFlow 재생성이 필요하다.

## 4. 열려 있는 선택지

### 4-1. leave 를 어떻게 보낼까

| 안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A. 기존 `RemoveAgent` 재사용** | 이미 스키마에 있는 `table RemoveAgent { actorId }` 를 해당 플레이어에게 보낸다. 클라 `Session.OnReceive` 에 `case RemoveAgent` 추가 | **스키마 변경 없음**(flatbuffers 재생성 불필요), 클라 변경 최소 | 액터 여러 개가 동시에 빠지면 메시지가 여러 개 |
| B. `UpdateActorNotify` 에 `removed:[int]` 추가 | 테이블 끝에 필드 append(하위호환) | 한 메시지에 묶여 효율적 | `syncnet.fbs` 재생성 필요(C++/C# 생성 코드 전체 갱신) |

leave 는 플레이어가 이동할 때만 발생하고 한 틱에 몇 개 수준이라, **A 로 시작하고 양이 문제되면 B 로 넘어가길 권장**한다.

### 4-2. 관심 집합을 어떻게 계산할까

| 안 | 방법 | 비용 | 비고 |
|---|---|---|---|
| **A. 매 틱 AoI 쿼리 + 집합 diff** | 플레이어마다 그리드 원형 쿼리 후 이전 집합과 비교 | 플레이어당 (셀 방문 + AoI 내 액터 수) | 단순. 반경 40/셀 2 면 플레이어당 1,681칸 방문 |
| B. 셀 구독 모델 | 플레이어가 셀을 옮길 때만 구독 셀 갱신, 액터 변경 시 그 셀 구독자에게만 전달 | 변경 액터 × 그 셀 구독자 수 | 정석이자 확장성 최고. 구독 테이블 유지 비용과 구현 복잡도가 큼 |

A 로도 **대역폭 목표는 100% 달성**한다. B 는 CPU 확장성 문제이며, A 를 먼저 넣고 측정한 뒤
필요하면 옮기는 편이 위험이 적다(측정 지표: 플레이어 수를 늘렸을 때 send/systems 단계 비용).

## 5. 작업 순서(제안)

1. `Map` 에 AoI 쿼리 + 플레이어별 `visible` 집합 도입, `SendWorldState` 를 플레이어 단위 조립으로 전환
2. leave 전송 경로(§4-1 선택안) + 클라 수신 처리
3. `SendStateTo` / 입장·게이트 이동 시 `visible` 초기화
4. `OnRemoveAgent` 에서 보고 있던 플레이어들에게 leave 통보
5. `Map.json` 에 `aoi_radius` 추가 + GameDataFlow 재생성
6. 검증: 단위 테스트(집합 diff 규칙: enter/stay/leave), 벤치(플레이어 수 대비 send/systems 비용),
   실서버 확인(멀리 갔다가 돌아오기, 시야 밖 몬스터 사망, 게이트 이동)

## 6. 구현 결과 (2026-07-30)

설계대로 구현했고 단위 테스트로 고정했다([AreaOfInterestTest.cpp](../../UnitTest/AreaOfInterestTest.cpp)).
`syncnet.fbs` 의 `UpdateActorNotify` 에 `removed:[int]` 를 append 하고 flatc 1.12.0(리포 동봉)으로
C++/C# 을 재생성했다. 클라는 [ActorSync.cs](../../Client/Assets/Scripts/GameObject/ActorSync.cs) 에서
`removed` 를 받아 사망 연출 없이 조용히 제거한다.

**단, 기본값은 꺼짐(`Map.json` 의 `aoi_radius: 0` = 맵 전체 브로드캐스트)이다.** 측정 결과가 이유다.

| 10,000마리 + 플레이어 50명 | 틱 |
|---|---|
| AoI 끔(브로드캐스트) | **9.58 ms** |
| AoI 반경 20 | 15.7 ms |
| AoI 반경 10 | 14.7 ms |
| AoI 반경 5 | 15.3 ms |

현재 맵은 한 변이 약 50유닛이라 **어떤 반경을 줘도 사실상 모두가 모두를 본다.** 걸러지는 액터가 없으니
플레이어별 메시지 조립(같은 액터를 사람 수만큼 중복 직렬화)만 남아 CPU 가 50~60% 늘었다.
AoI 는 맵이 시야 반경보다 충분히 클 때 이득이 나는 기법이고, 그 이득도 CPU 가 아니라 **대역폭**이다
(이 벤치는 세션이 없어 실제 송신을 재지 않는다).

그래서 스위치를 데이터로 두고 맵 크기에 맞춰 켜도록 했다. 큰 맵이 생기면 그 맵만 `aoi_radius` 를 준다.

구현 중 확인한 함정 하나: AoI 상태(구독 테이블 등)를 `Map` 멤버로 직접 늘렸더니 **AoI 를 꺼도**
틱이 느려졌다(10,000마리 기준 +6ms). 매 틱 액터마다 도는 `SyncActorState` 가 `Map` 의 멤버 배치에
민감해서다. 상태를 `Map::AoIState` 로 분리해 쓰는 맵에서만 할당하고, 켜짐 여부는 캐시된 bool 하나로
보도록 바꿔 해결했다.

### 뷰어 슬롯 도입 (2차)

셀 구독자 목록에 playerId 대신 **슬롯 인덱스**를 담도록 바꿨다. 뷰어 상태와 전송 대기열을
연속 배열(`AoIState::slots`)에 두고 셀에는 그 인덱스만 넣으므로, 매 틱 '변경 액터 × 구독자' 만큼
반복되던 해시 조회가 배열 색인으로 바뀐다(`QueueUpdate`).

구조는 분명히 나아졌지만, **이 벤치 환경에서는 총 틱 시간이 일관되게 줄지 않았다.**

| 10,000마리 + 50명 | 슬롯 도입 전 | 후 |
|---|---|---|
| AoI 끔 | 9.58 ms | 10.3 ms |
| 반경 20 | 15.7 ms | 14.2 ms |
| 반경 10 | 14.7 ms | 18.3 ms |
| 반경 5 | 15.3 ms | 20.6 ms |

반경을 줄일수록 비싸지는(=단조롭지 않은) 결과가 나오는데, 이건 최적화의 성패라기보다
**측정 환경이 AoI 를 평가하기에 부적절하다**는 신호다. 맵이 약 50유닛이라 어떤 반경에서도
모두가 모두를 보고, 몬스터가 소수 좌표에 극단적으로 쌓여 셀 밀도가 현실과 다르다.
이 상태에서 더 미세 조정하는 것은 근거 없는 추측이 된다.

### 남은 일

1. **평가 환경부터 만들기** — 시야 반경보다 충분히 큰 맵 + 현실적인 밀도의 스폰 분포.
   그 전에는 켠 상태의 CPU 튜닝을 진행하지 않는다.
2. **대역폭 측정** — 세션을 붙인 부하 테스트로 실제 송신량을 재야 AoI 의 본래 이득이 수치로 남는다.
   (지금 벤치는 세션이 없어 직렬화까지만 하고 송신을 재지 않는다.)
3. 위 둘이 준비되면 반경을 튜닝하고 해당 맵에서 켠다. 겹치는 시야의 중복 직렬화를 줄이는
   지역별 메시지 공유도 그때 검토한다.

## 7. 검증 항목

- 시야에 들어온 액터가 **한 번은 전체 스냅샷**으로 전달된다(클라가 생성 가능).
- 시야에서 벗어난 액터는 leave 로 제거되고, **사망 연출이 재생되지 않는다**.
- 시야 밖에서 제거된 액터가 클라에 남지 않는다.
- 멀어졌다 돌아오면 다시 enter 로 재생성된다(중복 생성 없음).
- 게이트 이동 후 이전 맵 액터가 남지 않는다(현재 씬 로드로 처리되는 부분과 충돌 없는지).
