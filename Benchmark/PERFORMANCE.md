# 성능 측정 기록 — 월드 틱(World::update)

`BM_WorldTick` 이 무거워 병목을 찾고 개선한 기록이다. 수치는 전부 실측이고, 재현 명령을 함께 적는다.

## 측정 환경

- 빌드: `Benchmark.vcxproj` **Release / x64** (Debug 수치는 의미 없음 — `ENABLE_BT_DEBUG` 가 켜지고 최적화가 꺼진다)
- 서버 틱: `kTickDt = 1/30` 초. **30Hz 기준 한 틱 예산은 33ms**
- 몬스터는 `Starting Village`(primary map)에 스폰. 월드에는 맵 4개가 살아 있다
- 명령:

```bash
cd Benchmark/x64/Release
./Benchmark.exe --benchmark_filter="BM_WorldTick/" --benchmark_min_time=0.5
./Benchmark.exe --benchmark_filter="BM_WorldTickPhases/crowd" --benchmark_min_time=0.5
./Benchmark.exe --benchmark_filter="BM_DetectEnemyOnly|BM_BT" --benchmark_min_time=0.5
```

## 1. 어디가 느린가 — 단계별 분해

`Map::update` 는 네 단계(actors → movement → systems → send)로 나뉘어 있고
[`BM_WorldTickPhases`](WorldBenchmark.cpp) 가 각 단계를 개별 계측한다.

**개선 전 (primary 맵 기준, 이동 전략 `crowd` 강제)**

> ⚠️ 1차 측정은 벤치마크가 `crowd` 를 강제 주입한 조건이었다. 프로덕션 필드 맵은
> `GameMode.json` 의 Field(id 1)가 지정한 **`waypoint`** 로 이미 돌고 있었으므로,
> 아래 movement 수치는 crowd 를 쓰는 맵에만 해당한다(§3 에서 바로잡았다).

| 몬스터 | 틱 총합 | actors(BT) | movement(dtCrowd) | systems(ECS) | send |
|---|---|---|---|---|---|
| 1 | 0.044 ms | 1.9 us (4%) | **41.3 us (94%)** | 0.4 us | 0.3 us |
| 1,000 | 4.59 ms | **2.93 ms (64%)** | 1.42 ms (31%) | 0.23 ms (5%) | 0.009 ms |
| 10,000 | 86.8 ms | **62.1 ms (71%)** | 16.3 ms (19%) | 8.35 ms (10%) | 0.08 ms |

한 마리당 한계비용은 actors 6.2us / movement 1.6us / systems 0.84us 였다.
스냅샷 생성·브로드캐스트(send)는 0.1% 미만으로 사실상 공짜다.

### 1-1. actors 안에서는 '탐지'가 아니라 'BT 프레임워크'가 범인

| 항목 | 10,000마리 | actors(62ms) 대비 |
|---|---|---|
| `BM_DetectEnemyOnly` (그리드 쿼리) | 5.31 ms | 8.6% |
| `BM_BTFrameworkTick_BTCpp` (1틱) | 1,582 ns | — |
| `BM_BTFrameworkTick_CodeBase` (1틱) | **58.4 ns** | — |

흔히 의심하는 적 탐지(그리드 스캔)는 actors 의 8.6% 뿐이었다. 같은 로직·같은 트리 구조인데
프레임워크만 다른 두 구현의 **단일 틱 비용이 27배** 차이가 났다.

### 1-2. 빈 맵도 매 틱 값을 치른다

몬스터 1마리인데 crowd 업데이트가 41us 다. [`CrowdNavMovement::MAX_AGENTS`](../Engine/World/CrowdNavMovement.h) 가
16384 이고, `dtCrowd::update` 는 [`getActiveAgents`](../recastnavigation/DetourCrowd.cpp) 등
**활성 여부와 무관하게 16384 슬롯을 훑는 루프**를 매 틱 여러 번 돈다.

`BM_WorldTick/1`(모든 맵) 268us vs `BM_WorldTickPhases/crowd/1`(primary 맵만) 44us —
차액 ~224us 는 **몬스터가 하나도 없는 나머지 3개 맵**이 쓰는 비용이다. 맵당 약 70us, 맵 수에 비례해 늘어난다.

### 1-3. 이동 전략 차이

10,000마리 movement: **crowd 18.4ms vs waypoint 0.65ms (28배)**. 군집 회피를 포기할 수 있는
맵이라면 전략 선택만으로 큰 차이가 난다.

## 2. 조치 #1 — 몬스터 BT 백엔드를 인하우스로 교체

두 백엔드는 [MonsterBT.cpp](../Engine/AI/MonsterBT.cpp)(behaviortree_cpp, `GameData/Monster.xml`)와
[MonsterCodeBaseBT.cpp](../Engine/AI/MonsterCodeBaseBT.cpp)(인하우스 `../BehaviorTree`)로,
트리 구조와 노드 로직이 1:1 로 같다. 바꾼 내용은 두 가지다.

1. **기본 백엔드를 `CodeBase` 로 변경** ([Monster.cpp](../Engine/Actor/Monster.cpp))
2. **선택된 백엔드의 트리만 생성**. 예전에는 몬스터마다 두 트리를 모두 만들고 하나만 틱했다 —
   쓰지도 않는 트리를 위해 스폰마다 `Monster.xml` 을 읽어 파싱했고, 메모리·캐시도 그만큼 낭비했다.

부수 작업: 인하우스 노드에 없던 `Monster dead` / `Monster destoryed` 로그를 맞춰 넣었고,
백엔드 전환이 AI 동작을 바꾸지 않음을 [MonsterBTTest.cpp](../UnitTest/MonsterBTTest.cpp)
(탐지→공격 / 배회 / 사망 분기를 두 백엔드로 각각 검증)로 고정했다.

> 대가: BT 디버그 뷰어(`BTDebugManager`)는 behaviortree_cpp 트리에만 붙는다.
> 뷰어가 필요하면 몬스터 스폰 **전에** `Monster::btBackend_ = BTBackend::BTCpp` 로 되돌린다
> (트리는 스폰 시점에 결정된다).

## 3. 조치 #2 — 이동 전략 기본값을 waypoint(경로 추종)로 통일

먼저 정정할 것: **필드 맵은 이미 waypoint 로 돌고 있었다.** `GameMode.json` 의 Field(id 1)가
`"movement": "waypoint"` 이고 [World::Init](../Engine/World/World.cpp) 이 그 값을 그대로 쓴다.
§1 의 movement 수치(10,000마리 16.3ms)는 벤치마크가 `crowd` 를 강제 주입한 값이라
프로덕션에는 해당하지 않았다. 그래서 "movement 가 최대 병목" 이라는 §1 의 결론은 crowd 를 쓰는 맵에만 유효하다.

남아 있던 crowd 경로를 정리했다.

1. [`NavMovementFactory::ParseType`](../Engine/World/NavMovementFactory.cpp) 의 **폴백을 crowd → waypoint**.
   데이터에 `movement` 가 없거나 오타면 예전에는 조용히 crowd 로 떨어졌다.
2. `GameMode.json` 의 Raid(id 2) `movement` 를 **crowd → waypoint** (데이터상 마지막 crowd 사용처).
3. 벤치마크/유닛테스트의 기준 전략을 waypoint 로 맞춤. 그동안 벤치는 crowd 를 강제해
   프로덕션과 다른 값을 냈다. crowd 는 `BM_WorldTick10000/crowd`, `BM_WorldTickPhases/crowd` 로 비교용만 남긴다.

두 전략의 차이는 비용만이 아니다. **waypoint 는 군집 회피/분리(separation)가 없어 에이전트가 겹칠 수 있다.**
회피가 꼭 필요한 맵은 데이터에서 `"movement": "crowd"` 로 지정하면 그대로 동작한다(구현은 유지).

### 결과 (조치 #1 + #2 누적)

**월드 틱 전체 (`BM_WorldTick`, 맵 4개 포함)**

| 몬스터 | 최초(crowd+BT.CPP) | 조치 #1 후 | 조치 #2 후 | 누적 변화 |
|---|---|---|---|---|
| 1 | 268 us | 282 us | **1.34 us** | **-99.5%** |
| 64 | 449 us | 318 us | 18.6 us | -96% |
| 128 | 617 us | 334 us | 38.3 us | -94% |
| 256 | 950 us | 371 us | 85.5 us | -91% |
| 512 | 2,235 us | 850 us | 181 us | -92% |
| 1,000 | 4,646 us | 1,744 us | **608 us** | **-87%** |

1마리 틱이 268us → 1.34us 가 된 것이 §1-2 에서 지적한 **유휴 맵 고정비**다.
waypoint 는 활성 에이전트만 순회하므로 빈 맵은 사실상 공짜다.

**단계별 (primary 맵, waypoint)**

| 몬스터 | 틱 총합 | actors(BT) | movement | systems(ECS) | send |
|---|---|---|---|---|---|

스폰도 `BM_WorldSpawnMonsters/1000` 이 9.5 ms → **4.5 ms** 로 줄었다(crowd 의 addAgent 가 더 비싸다).

**최초 대비: 10,000마리 틱 86.8 ms → 14.0 ms (-84%).** 30Hz 예산(33ms) 안에 10,000마리가 들어온다.

## 4. 수용량 — 10Hz(틱당 100ms)에 몇 마리까지

서버 시뮬레이션은 10Hz([`GameServer::UpdateGameLogic`](../Engine/Server.cpp) 의 `SIM_RATE = 10`)이므로
한 틱 예산은 **100ms** 다. `BM_WorldTickCapacity`(몬스터만) 와 `BM_WorldTickCapacityEngaged`(플레이어 50명)로
`World::update` 를 직접 재고 `budget_pct = 틱 시간 / 100ms` 를 출력한다.

**배회만 (플레이어 0명)**

| 몬스터 | 틱 | 예산 대비 |
|---|---|---|
| 10,000 | 11.8 ms | 12% |
| 20,000 | 32.0 ms | 32% |
| 32,000 | 61.5 ms | 62% |
| **40,000** | **94.7 ms** | **95%** |
| 60,000 | 194 ms | 194% |

**교전 포함 (플레이어 50명이 스폰 좌표 전역에 분산)**

| 몬스터 | 틱 | 예산 대비 |
|---|---|---|
| 10,000 | 28.1 ms | 28% |
| 20,000 | 63.0 ms | 63% |
| **28,000** | **94.0 ms** | **94%** |
| 30,000 | 101.9 ms | 102% |
| 32,000 | 108.7 ms | 109% |

> 40,000 / 28,000 / 30,000 / 32,000 은 `--benchmark_repetitions=3` 중앙값이며 표준편차는 1~3ms 다.

**결론: 배회만이면 약 41,000마리, 플레이어 50명이 교전 중이면 약 29,000마리**에서 10Hz 예산이 찬다.
교전이 붙으면 같은 몬스터 수의 틱 비용이 **1.5~2.4배**로 뛴다 — 탐지가 매 틱 성공하면서
스태거링(`kDetectInterval`)이 무력화되고, `ActionChase` 가 매 틱 `SetMoveTarget` 을 불러
waypoint 전략이 그때마다 경로를 다시 계산하기 때문이다.

한 마리당 비용도 규모에 따라 커진다(10k 1.18us → 40k 2.37us). 액터 리스트/ECS 풀을 훑는
캐시 미스가 늘어난 영향으로, actors 와 systems 가 거의 같은 비율로 함께 증가한다.

### 측정 조건(그대로 믿으면 안 되는 것들)

- **단일 스레드** 기준이다(월드 로직은 한 스레드에서 돈다).
- 몬스터가 유효 스폰 좌표(수천 개)에 **겹쳐 쌓인다**. 실제 맵처럼 흩어지면 그리드 밀도가 달라진다.
- **실제 네트워크 송신이 없다.** 세션이 없어 `SendBroadcast` 가 직렬화까지만 하고 끝난다
  (send 단계가 0.1% 미만인 이유). 실서버는 접속자 수만큼 송신 비용이 더 붙는다.
- 벤치의 `dt` 는 `1/30` 인데 예산은 10Hz 기준으로 계산했다. 비용 자체는 dt 에 거의 무관하지만
  10Hz 로 돌리면 한 틱당 이동 거리가 3배라 경로 재계산 빈도가 달라질 수 있다.

## 5. 세부 프로파일 — 무엇이 실제로 비싼가

단계별 비중만으로는 "actors 가 크다"까지밖에 모른다. 그래서 틱 안에서 반복되는 작업 하나하나의
단가를 격리해 쟀다(`BM_NavPathIssue`, `BM_SerializeActorsOnly`, `BM_DetectEnemyOnly`, `BM_Grid*`).

| 작업 | 1회 비용 | 언제 발생하나 |
|---|---|---|
| **경로 산출** `Patrol`(임의 지점+경로) | **9.46 us** | 배회 목적지 도달/휴식 종료마다 |
| **경로 산출** `SetMoveTarget` | **4.07 us** | **교전 중 매 틱**(`ActionChase`) |
| 적 탐지 스캔 `getCharactersInViewRange` | 0.45 us | 배회 10틱당 1회 / 교전 중 매 틱 |
| ActorInfo 직렬화 `GetActorInfo` | 0.10 us | 위치가 바뀐 액터마다 매 틱 |
| 그리드 셀 이동(재등록) | 0.095 us | 셀 경계를 넘을 때 |
| 그리드 셀 내 이동 | 0.007 us | 그 외 매 틱 |

**경로 산출이 다른 작업보다 10~100배 비싸다.** 그리고 교전 중인 몬스터는 그 비용을 매 틱 낸다 —
[`ActionChase`](../Engine/AI/MonsterCodeBaseBT.cpp) 가 틱마다 `SetMoveTarget` 을 부르고,
waypoint 전략은 호출마다 `dtNavMeshQuery` 로 경로를 새로 낸다.

§4 의 교전 측정이 이걸 뒷받침한다. 10,000마리 기준 플레이어가 없으면 11.8ms, 50명이 교전하면 28.1ms 로
**+16.3ms** 인데, 이는 교전 중 몬스터 수 × 4.07us 규모(≈4,000마리 상당)와 맞아떨어진다.
즉 **교전 시 늘어난 비용은 사실상 전부 경로 재계산이다.**

직렬화는 10,000마리 전원 기준 1.01ms 로 systems 단계(3.5ms)의 **약 29%** 다.
관전자(플레이어)가 없어도 `SyncActorState` 가 액터마다 flatbuffer 를 만든다.

## 6. 그리드(GridManager) 별도 분석

`GridManager(100, 100, 2)` — 셀 2유닛, 100×100 셀(`GridVector`, 평면 배열). 측정은 `BM_Grid*`.

| 항목 | 10,000 | 40,000 |
|---|---|---|
| 탐지 스캔 전원 1회 (캐릭터 0명) | 4,523 us | 21,629 us |
| 탐지 스캔 전원 1회 (캐릭터 50명) | 4,655 us | 21,941 us |
| 탐지 스캔 전원 1회 (캐릭터 500명) | 5,970 us | — |
| 셀 이동(재등록 발생) | 955 us | 4,472 us |
| 셀 내 이동(재등록 없음) | 72.8 us | 294 us |
| AoE 쿼리 1회(반경 5) | 2.42 us | 5.56 us |

여기서 나오는 문제 세 가지다.

1. **탐지 비용이 캐릭터 수와 무관하다.** 캐릭터가 0명이어도 4.5ms 가 든다(50명일 때와 3% 차이).
   `range 10 / cellSize 2` 라 한 번 스캔에 `(2*5+1)² = 121` 셀을 방문하는데, 대부분 빈 셀이고
   비용은 **셀 방문 자체**(경계 검사 + `IGrid::get()` 가상 호출 + `empty()`)다.
   캐릭터는 보통 몬스터보다 훨씬 적으므로, 캐릭터가 있는 셀만 따로 인덱싱해 순회하면
   O(121 셀) → O(캐릭터 수) 로 바뀐다.
2. **`Cell` 이 `unordered_set` 두 개다.** 그래서 셀 이동이 셀 내 이동보다 **13배** 비싸다
   (7.3ns → 95.5ns). 노드 할당/해제와 해싱 때문이다. `std::vector` + swap-erase 로 바꾸면
   이동뿐 아니라 순회 지역성도 좋아지고, 셀 내용을 벡터로 복사하는 `getEntitiesInAoEMask` 도 함께 빨라진다.
3. **셀 접근이 가상 호출이다.** `IGrid::get()` 이 가상이라 셀 방문마다 간접 호출이 붙는다.
   구현이 둘(`GridVector`/`GridHashMap`)뿐이고 맵 생성 시 고정되므로, 핫 경로에서는
   구체 타입으로 분기하거나 인덱스 계산을 인라인화할 수 있다.

AoE 쿼리는 스킬 시전 때만 발생하고 1회 2~6us 라 손댈 이유가 없다.

## 7. 조치 #3 — 추격 경로 재사용

[`WaypointNavMovement::SetMoveTarget`](../Engine/World/WaypointNavMovement.cpp) 이 목표가 거의
그대로면(이동 < `kRepathDistance` = 1.5, 몬스터 공격 사거리 3보다 작다) 기존 경로를 재사용한다.
BT 노드는 건드리지 않았다 — 이동 전략이 스스로 캐시하므로 두 BT 백엔드와 이후의 모든 호출자가 함께 이득을 본다.
`Patrol` 도 산출한 목적지를 경로 목표로 기록해, 배회 중 추격 지시가 들어오면 정상적으로 재계산된다.

| 항목 | 전 | 후 |
|---|---|---|
| `SetMoveTarget` 반복 호출 1회 | 4.07 us | **0.005 us** |
| 틱 10,000마리 + 플레이어 50명 | 28.1 ms | **20.6 ms** (-27%) |
| 틱 20,000마리 + 플레이어 50명 | 63.0 ms | 53.4 ms (-15%) |
| 틱 32,000마리 + 플레이어 50명 | 108.7 ms | 96.1 ms (-12%) |

배회만 하는 경우(플레이어 0명)는 설계상 영향이 없다 — `Patrol` 은 매번 새 목적지를 내므로 재사용 대상이 아니다.

**정정**: §5 에서 "교전 시 늘어난 비용(+16.3ms)은 사실상 전부 경로 재계산" 이라고 적었는데 틀렸다.
경로 재계산을 없앤 뒤에도 절반가량(+8.8ms)이 남는다. 다시 재보니 원인은 **탐지**였다.

| 탐지 전원 1회 스캔(10,000마리) | 캐릭터 0명 | 캐릭터 50명 |
|---|---|---|
| `Map::DetectEnemy` | 4.70 ms | **9.56 ms** |

캐릭터가 있으면 후보마다 navmesh 시야 판정(`Raycast`, 1회 **0.353 us**)이 붙어 탐지 단가가 두 배가 된다.
게다가 교전 중(`targetActorId_ >= 0`)에는 스태거링이 꺼져 **매 틱** 전체 스캔을 돈다.
즉 남은 교전 비용의 주범은 "교전 중 매 틱 전체 재탐색"이다.

## 8. 조치 #4 — 교전 중에는 재탐색 대신 타깃 검증

교전 중(`targetActorId_ >= 0`)에는 스태거링이 꺼져 **매 틱 전체 스캔**을 돌고 있었다.
이미 대상을 잡고 있는데 시야 반경의 모든 셀을 훑고 후보마다 시야 판정을 하는 셈이다.

[`Map::IsTargetVisible`](../Engine/Map/Map.cpp) 을 추가해, 교전 중에는 **그 대상 하나만**
검증한다(맵에 존재 + 시야 반경 + 가림 없음 = 거리 1회 + `Raycast` 1회). 검증에 실패하면
타깃을 놓고 기존의 스태거링된 전체 탐색으로 떨어진다. 두 BT 백엔드 모두 같은 로직으로 고쳤다.

> 설계 주의: 검증 조건은 `DetectEnemy` 와 **정확히 같아야 한다.** 처음에 검증에만
> "사망 대상 제외"를 넣었더니, 놓친 대상을 바로 다음 전체 탐색이 다시 잡아 타깃이 매 틱
> 붙었다 떨어지는 진동이 생겼다(단위 테스트가 잡았다). 시체를 쫓지 않게 하려면
> 두 경로를 함께 고쳐야 하며, 그건 성능이 아니라 AI 사양 변경이다.

부수 효과로 **타깃이 더 이상 흔들리지 않는다.** 예전에는 매 틱 전체 스캔의 '첫 번째 후보'를
다시 잡아 근처에 캐릭터가 여럿이면 대상이 바뀔 수 있었지만, 이제 유효한 동안 처음 잡은 대상을 유지한다.

### 결과 (조치 #3 + #4 누적, 플레이어 50명 교전)

| 20,000 | 63.0 ms | 53.4 ms | 37.8 ms | -40% |
| 32,000 | 108.7 ms | 96.1 ms | 74.7 ms | -31% |

10,000마리 기준 교전 틱(9.07ms)이 배회 전용(8.59ms)과 거의 같아졌다 — **교전 오버헤드가 사실상 사라졌다.**
규모가 커지면(40,000) 교전 중 몬스터가 많아져 검증 비용과 공격 시전이 쌓이므로 차이가 다시 벌어진다(+29%).

## 9. 조치 #5 — 관전자 없으면 직렬화하지 않는다

`SendWorldState` 가 메시지를 조립했는데, **그 맵에 플레이어가 한 명도 없어도** 그대로 돌았다.
이제 `players_.empty()` 면 위치·그리드 갱신만 하고 직렬화와 메시지 조립을 건너뛴다
(제거 대기 액터 정리는 그대로 수행한다).

> 이건 "볼 사람이 없을 때"만 해결한다. 실서버의 본질적 낭비 — 플레이어가 있으면 **맵의 모든 액터**를
> **모든 플레이어**에게 보낸다 — 는 그대로다. 관심영역(AoI) 필터는 §10 참고.

## 10. 조치 #6 — 그리드 자료구조 교체

## 11. 조치 #7 — 관심영역(AoI) 도입, 그리고 기본값을 끔으로 둔 이유

플레이어별로 주변 셀만 구독해 시야 안의 액터만 보내는 구조를 넣었다(설계·구현 상세는
[AOI_DESIGN.md](../Engine/Map/AOI_DESIGN.md)). 목적은 CPU 가 아니라 **대역폭**이다 —
지금은 40,000마리 맵이면 플레이어 한 명당 매 틱 40,000개 액터 정보가 나간다.

측정해 보니 현재 맵에서는 켜면 손해다.

| 10,000마리 + 플레이어 50명 | 틱 |
|---|---|
| AoI 끔(브로드캐스트) | **9.58 ms** |
| AoI 반경 20 | 15.7 ms |
| AoI 반경 10 | 14.7 ms |
| AoI 반경 5 | 15.3 ms |

맵 한 변이 약 50유닛이라 **어떤 반경을 줘도 모두가 모두를 본다.** 걸러지는 액터가 없으니
플레이어별 메시지 조립(같은 액터를 사람 수만큼 중복 직렬화)만 남아 CPU 가 50~60% 늘었다.
그래서 `Map.json` 의 `aoi_radius` 를 0(끔)으로 두고, 맵이 시야 반경보다 충분히 커질 때 그 맵만 켠다.

이어서 셀 구독자 목록을 playerId → **슬롯 인덱스**로 바꿔 전달 경로의 해시 조회를 없앴지만
(`QueueUpdate` 가 배열 색인으로 끝난다), 총 틱 시간은 이 환경에서 일관되게 줄지 않았다
(반경 20: 15.7→14.2ms, 반경 10: 14.7→18.3ms, 반경 5: 15.3→20.6ms). 반경을 줄일수록 비싸지는
비단조 결과 자체가 **이 벤치가 AoI 평가에 부적합**하다는 신호다 — 맵이 작아 모두가 모두를 보고,
몬스터가 소수 좌표에 쌓여 셀 밀도가 현실과 다르다. 그래서 켠 상태의 튜닝은
평가 환경(큰 맵 + 현실적 분포 + 대역폭 측정)을 갖춘 뒤로 미뤘다([AOI_DESIGN.md](../Engine/Map/AOI_DESIGN.md)).

**뒤에 밝혀진 것(13절)**: 이 벤치는 `Map::Enter` 를 부르지 않아 `players_` 가 늘 비어 있었고,
그래서 `SendWorldState` 가 통째로 조기 반환했다. 위 표의 차이는 전송/직렬화가 아니라
구독 관리 비용만 잡은 것이라 신뢰하기 어렵다.

> 구현 중 만난 함정: AoI 상태를 `Map` 멤버로 직접 늘렸더니 **AoI 를 꺼도** 틱이 느려졌다
> (10,000마리 + 50명 기준 9.6ms → 15.2ms). 매 틱 액터마다 도는 `SyncActorState` 가 `Map` 의
> 멤버 배치에 민감해서다. 상태를 별도 객체(`Map::AoIState`)로 빼 쓰는 맵에서만 할당하고,
> 켜짐 여부를 캐시된 bool 로 보게 고쳐 원복했다. **끄면 비용이 0이어야 한다**는 것이 이 기능의 조건이다.

## 12. 조치 #8 — 그리드 크기를 네비메시 범위에서 뽑는다

AoI 평가 환경을 만들려고 500x500 맵(Arcadia Plains)을 추가하다가 발견한 문제다.

`Map::Init` 은 `GridManager(100, 100, 2)` 로 고정이라 월드 좌표 **±100 만** 담았다. 그 밖의 액터는
[`enterCell`](../Engine/Grid/GridManager.cpp) 이 범위 검사에 걸려 조용히 return 하므로 **어떤 셀에도
들어가지 않는다.** 결과는 크래시가 아니라 조용한 오작동이다.

- 적 탐지 — 캐릭터가 121명 이하면 맵 전체 목록을 훑는 경로라 우연히 동작하고, 넘으면 셀 스캔으로
  바뀌면서 서로 못 본다
- AoI 셀 구독 — 전부 셀 기반이라 동작하지 않는다(측정하려던 기능이다)
- 스킬 AoE 판정(`getEntitiesInAoEMask`) — 셀 기반이라 아무도 맞지 않는다

500x500 맵이면 면적의 84%가 이 상태였다.

**네비메시 타일 헤더의 경계**(`NavMesh::Bounds`)에서 그리드 크기와 원점을 계산하도록 고쳤다.
`Map.json` 의 `size` 는 쓰지 않는다 — 툴이 씬 경계에서 채우는 메타데이터일 뿐 엔진이 참조한 적이
없어서, 실제 지오메트리가 50유닛인 맵에 1000 이 적혀 있는 식으로 어긋나 있다.

기존 맵도 크기가 바뀐다(Starting Village: 100x100 → **29x28 셀**, 실제 범위가 약 51x50 이므로).

### 원점은 셀 크기의 배수로 맞춰야 한다

네비메시 경계를 그대로 원점으로 쓰면(-28.3) 느려진다.

| 10,000마리 배회 | 틱 |
|---|---|
| 고정 그리드 100x100 (기존) | 6.92 ms |
| 네비메시 크기, 원점 -28.3 (정렬 안 함) | 7.74 ~ 7.94 ms |
| 네비메시 크기, 원점 -30.0 (셀 배수로 내림) | **6.77 ms** |

셀 경계가 소수점에 걸리면 정수 좌표에 서 있는 액터가 부동소수 오차로 매 틱 셀을 넘나들며
`leave`+`enter` 를 반복한다. 원점을 배수로 내리면 (좌표 - 원점) 이 이진수로 정확히 떨어져 사라진다.
`getCellCoord` 의 나눗셈을 역수 곱셈으로 바꿔도 보면 이 차이는 그대로였다 — 연산 비용이 아니라
셀 전이 횟수 문제였다.

수용량은 변화 없다(10,000마리 6.87 → 6.77 ms, 40,000마리 70.4 → 74.1 ms, 표준편차 2.95ms).

## 13. 큰 맵(500x500)에서 다시 재기

여기까지의 수치는 전부 primary 맵(Starting Village, 실제 약 51x50유닛)에서 나온 것이다.
`ValidSpawns` 의 좌표 훑기가 `x:[-26,26]` 로 박혀 있어서, 몬스터를 몇 마리로 늘리든
**한 줌의 좌표에 쌓였다.** Arcadia Plains(500x500, navmesh 이동 가능 면적 184,328m²)가
완성되어 실제 분포로 다시 쟀다.

`BM_LargeMapTickCapacity` / `BM_LargeMapTickCapacityEngaged` 를 추가했다. 스폰 좌표는
격자를 훑는 대신 **navmesh 폴리곤을 면적 비례로 표본**해서 뽑는다(맵툴의 스폰 자동 배치와 같은 방식).
대상 맵은 `World::GetMaps()` 중 navmesh 범위가 가장 넓은 것을 고른다.

### 먼저 고쳐야 했던 것 — 콜드 스타트를 재고 있었다

첫 측정은 이렇게 나왔다.

| 몬스터 | 틱 | 반복 |
|---|---|---|
| 10,000 | 12.5 ms | 100 |
| 20,000 | **1,044 ms** | **1** |

60배 절벽은 성능 특성이 아니라 측정 오류다. **스폰 직후 첫 틱은 몬스터 전원이 같은 틱에
배회 목적지를 잡고 경로를 계산**해서 정상 틱보다 수십 배 비싸다. 그 한 틱이 `min_time` 1초를
혼자 채워 버리니 google benchmark 는 반복을 1회로 확정하고, 결과적으로 정상 상태가 아니라
콜드 스타트를 보고했다. 워밍업 10틱을 넣고 콜드 스타트는 `first_tick_ms` 로 따로 기록하게 했다.

### 수용량 — 맵 크기는 틱 비용을 바꾸지 않는다

몬스터만, 10Hz 예산 100ms 기준(중앙값, 반복 3회).

| 몬스터 | Starting Village(약 51유닛) | Arcadia Plains(500유닛) | 예산 |
|---|---|---|---|
| 10,000 | 9.20 ms | 8.92 ms | 8.9% |
| 20,000 | 21.4 ms | 23.9 ms | 23.9% |
| 40,000 | 51.0 ms | 53.8 ms | 53.8% |
| 60,000 | 84.7 ms | 81.8 ms | 81.8% |

**차이가 없다.** 500x500 에 흩뿌려도 좁은 맵에 쌓아도 틱 비용이 같다 — 조치 #8 의 그리드가
맵 크기에 맞춰 커지면서 셀당 밀도가 유지되기 때문이다. 수용 한계는 두 맵 모두 **약 70,000마리**다.

플레이어 50명이 붙어 교전하면(Arcadia):

| 몬스터 + 플레이어 50 | 틱 | 예산 |
|---|---|---|
| 10,000 | 13.5 ms | 13.5% |
| 20,000 | 32.0 ms | 32.0% |
| 40,000 | 66.3 ms | 66.3% |

### 콜드 스타트는 맵이 커질수록 비싸다

`first_tick_ms`(스폰 직후 첫 틱):

| 몬스터 | Starting Village | Arcadia Plains |
|---|---|---|
| 10,000 | 110 ms | 526 ms |
| 20,000 | 213 ms | 1,058 ms |
| 40,000 | 425 ms | 2,100 ms |
| 60,000 | 676 ms | 3,117 ms |

약 5배다. 넓은 맵에서는 경로가 길고 navmesh 폴리곤도 많아(16,313개) A* 한 번이 훨씬 비싸다.
서버 기동 시 `World::SpawnMapMonsters` 가 전원을 한 틱에 스폰하므로, 몬스터가 많은 맵은
**기동 직후 수 초의 스톨**이 생긴다. 스폰을 여러 틱에 나누거나 첫 배회를 분산시키면 사라진다.

### 관심영역(AoI) — 이 벤치로는 아직 답이 안 나온다

10,000마리 + 플레이어 50명, Arcadia:

| 반경 | 틱 |
|---|---|
| 0 (끔, 전체 브로드캐스트) | 13.5 ms |
| 100 | 19.5 ms |
| 50 | 14.3 ms |
| 25 | 15.2 ms |

반경 50 과 25 의 차이(14.3 / 15.2)는 표준편차(약 1.2ms) 안이라 구분되지 않고, 여전히 **끈 쪽이
제일 싸다.** 이유는 11절과 같지 않다 — 이번엔 맵이 충분히 크다. 이번 이유는 **비교가 공정하지
않아서**다. 브로드캐스트는 메시지를 한 번만 만들어 전원에게 보내는데, 벤치의 Player 는 세션이
없어서 **보내는 비용이 0** 이다. 반면 AoI 는 뷰어마다 메시지를 조립하므로 그 비용은 그대로 든다.
즉 지금 재고 있는 것은 "AoI 의 CPU 오버헤드"뿐이고, AoI 가 줄이려는 **대역폭은 아예 재지 않는다.**

결론을 내려면 맵이 틱마다 직렬화해 내보내는 **바이트 수**를 세야 한다. 그 계측을 넣기 전까지
`aoi_radius` 는 계속 0(끔)이다.

### 벤치가 드러낸 엔진 버그 — 플레이어가 남은 채로 맵을 파괴하면 죽는다

큰 맵 교전 벤치를 처음 돌렸을 때 측정이 끝난 뒤 세그폴트가 났다. 위치는 `Map::~Map` 이다.

소멸자는 `actorMap_`/`actorList_` 를 먼저 비워 액터가 `systemManager_` 보다 먼저 파괴되게 하지만,
**`players_` 는 비우지 않았다.** 맵에 남아 있는 플레이어가 자기 캐릭터를 `shared_ptr` 로 붙들고
있으면 그 액터는 거기서 죽지 않고 `delete systemManager_` 이후까지 살아남아, `Actor::Clear` 가
이미 파괴된 `systemManager_` 를 건드린다.

벤치 전용 문제가 아니다 — **플레이어가 접속한 채로 서버를 내리면 종료 시 같은 경로로 죽는다.**
소멸자에서 남은 플레이어의 `UnPossess()` 를 먼저 호출하도록 고쳤다.

지금까지 이 경로가 안 드러난 이유는, 기존 교전 벤치가 `Map::Enter` 를 부르지 않아
`players_` 가 늘 비어 있었기 때문이다. 그래서 그 벤치는 **`SendWorldState` 의 조기 반환에 걸려
직렬화/전송 단계를 통째로 건너뛰고 있었다**(9절의 "관전자 없으면 직렬화하지 않는다"가 항상 참).
11절의 AoI 반경 비교가 비단조로 나온 것도 이 때문일 가능성이 크다.

## 14. 남은 병목과 다음 순서

10,000마리 기준 현재 비중이다.

| 단계 | 시간 | 비중 |
|---|---|---|
| actors (BT) | 8.22 ms | 59% |
| systems (ECS) | 5.46 ms | 39% |
| movement (waypoint) | 0.24 ms | 1.7% |
| send | 0.06 ms | 0.4% |

1. **actors** — 이제 프레임워크 오버헤드가 아니라 노드 안의 실제 작업이다.
   `BM_DetectEnemyOnly` 로 탐지 비중을 다시 재고, 스태거링 간격(`kDetectInterval`)이나
   그리드 쿼리 자체를 손볼지 판단한다.
   > **18절에서 처리했다.** 진단이 반만 맞았다 — 비싼 것은 노드의 일이 아니라 전원이 매 틱
   > 트리를 순회하는 구조였다. AI 를 ECS(배치 패스 + 사고 스케줄)로 재구성해 actors 가
   > 10,000마리 기준 2.08ms → 0.63ms 가 됐다.
2. **systems** — 위치 변경 감지/ActorInfo 누적이 39%까지 올라왔다. 변경 없는 액터를 빨리 걸러내는 쪽.
3. **movement / send** — 손댈 이유 없음.

## 15. 존 그래프 — 맵을 넘나드는 경로 탐색

월드 틱과는 성격이 다른 비용이다. 재는 것은 둘.

- **빌드**: 기동 시 1회. 맵마다 게이트끼리 도보 간선을 만든다 — `O(맵 × 게이트²)`.
- **탐색**: 요청마다. 다익스트라 한 번.

실제 `Map.json` 은 맵 6개 / 정점 7개라 규모를 볼 수 없다. 그래서 W×H **격자 세계**를 합성해
잰다(`UnitTest/SyntheticMaps.h` — 단위 테스트가 최단 경로 정확성을 검증하는 것과 같은 위상이라,
측정치와 검증이 같은 대상을 가리킨다). 맵 하나가 격자 한 칸이고 상하좌우 이웃과 two_way 로 이어진다.

```bash
cd Benchmark/x64/Release
./Benchmark.exe --benchmark_filter="ZoneGraph|NavMeshPathLength"
```

### 빌드 — 간선 수에 선형

| 격자 | 맵 | 정점 | 간선 | 시간 | 간선당 |
|---|---|---|---|---|---|
| 4×4 | 16 | 48 | 152 | 11.8 us | 78 ns |
| 8×8 | 64 | 224 | 808 | 58.5 us | 72 ns |
| 16×16 | 256 | 960 | 3,656 | 261 us | 71 ns |
| 32×32 | 1,024 | 3,968 | 15,496 | 1,321 us | 85 ns |

맵당 게이트를 늘리면(이웃 한 쌍당 문 여러 개) 간선이 제곱으로 늘어난다. 8×8 고정:

| 이웃당 문 | 맵당 게이트 | 간선 | 시간 |
|---|---|---|---|
| 1 | ~4 | 808 | 58.5 us |
| 2 | ~8 | 3,232 | 142 us |
| 4 | ~16 | 12,928 | 382 us |
| 8 | ~32 | 51,712 | 1,018 us |

**문 개수가 2배면 빌드 시간이 ~2.6배다.** 맵 수보다 맵당 게이트 수가 훨씬 위험한 축이다.

### 그런데 진짜 비용은 navmesh 실측이다

위 표는 도보 비용을 **직선 거리**로 잰 값이라 Detour 쿼리가 빠져 있다. 실제 빌드는
간선마다 `NavMesh::PathLength`(findPath + findStraightPath)를 한 번씩 부른다.

| 맵 | 표본 | 쿼리 1회 |
|---|---|---|
| Starting Village (작은 맵) | 3 | **1.66 us** |
| Arcadia Plains (500×500) | 200 | **181 us** |

큰 맵에서 간선 하나가 181us 다. 그래프 구성 자체(~80ns)보다 **2,000배** 비싸다.
즉 실제 빌드 시간은 사실상 `실측 간선 수 × 이 값` 이다.

표본은 맵을 가로지르는 긴 경로다(스폰 마커 200개를 반씩 건너뛰며 짝지었다). Detour 는 훑는
폴리곤 수에 비례하므로 가까운 게이트끼리는 이보다 싸다 — 아래는 **상한** 으로 읽으면 된다.

| 500×500 맵의 게이트 수 | 도보 간선(쌍) | 그 맵 하나의 빌드 시간(상한) |
|---|---|---|
| 4 | 6 | 1.1 ms |
| 10 | 45 | 8.1 ms |
| 20 | 190 | 34 ms |

**이것이 `Map.json` 의 `gate_links` 가 있는 이유다.** 적어 두면 그 간선은 Detour 를 건너뛴다.

지금 실데이터 빌드는 **1.86 us** 인데(정점 7 / 간선 10), 이는 navmesh 로 재는 간선이 하나도
없기 때문이다 — 맵 안에 게이트가 둘 이상인 곳이 맵 2 뿐이고 그건 이미 `gate_links` 에 적혀 있다.
지금 값이 싸다고 안심할 게 아니라, 위 표가 앞으로 물게 될 값이다.

### 탐색 — 가까운 곳은 싸고 먼 곳은 비싸다

| 정점 | 이웃 맵 | 대각선 끝 | 길 끊김 | AreConnected |
|---|---|---|---|---|
| 48 | 0.77 us | 2.15 us | — | — |
| 224 | 0.76 us | 8.13 us | 3.74 us | 2.01 us |
| 960 | 0.88 us | 35.3 us | 16.0 us | 7.36 us |
| 3,968 | 1.36 us | 365 us | 133 us | 48.6 us |

- **이웃 맵으로 가는 조회는 그래프 크기와 거의 무관하게 ~1us** 다. 다익스트라가 목적지를
  확정하는 순간 멈추므로, 정점이 80배 늘어도 1.8배밖에 안 는다. 흔한 요청은 싸다.
- **대각선 끝(62번 전환)은 365us** 로, 정점 4.1배에 시간 10.3배다. 선형보다 나쁜 이유는
  인접 리스트가 정점마다 따로 힙에 있어서 그래프가 L2(524K)를 넘는 순간 캐시 미스가
  지배하기 때문이다. 고치려면 CSR(평탄 배열)로 바꿔야 하는데, **지금 실데이터는 정점 7개고
  이 쿼리는 틱마다 부르는 것이 아니라 미룬다.**
- **연결 여부만 필요하면 `AreConnected` 가 7.5배 싸다**(48.6us vs 365us). 비용을 계산하지
  않고 포탈만 따라가는 BFS 라서다.

### 없는 맵 조회를 걸러냈다

처음 측정에서 **없는 맵 id 로 물으면 371us** 가 나왔다. 도달 가능한 정점을 전부 훑고 나서야
"없다"고 답하기 때문이다. 클라가 보낸 맵 id 로 조회하는 자리라면 그 자체가 부하가 된다.

탐색 시작 전에 출발/목적 맵이 그래프에 있는지 먼저 보게 고쳤다.

| | 이전 | 이후 |
|---|---|---|
| 없는 맵 id (정점 3,968) | 371 us | **0.012 us** |

맵은 있는데 길이 끊긴 경우(133us)는 이렇게 걸러낼 수 없다 — 다 훑어야 없는 걸 안다.
그쪽이 잦다면 `AreConnected` 결과를 캐시하는 편이 맞다.

## 16. 멀티스레드 멀티 월드 — 한 프로세스 수용량

여기까지의 수치는 전부 **월드 하나를 한 스레드에서** 돌린 값이다. 운영 서버는
`ServerConfig.world.thread_count` 개의 스레드에 월드(포트 하나당 `GameServer` 하나)를
라운드로빈으로 배정하고, 한 월드는 항상 같은 스레드에서만 갱신한다
(`ServerManager::IoWorker`). `BM_MultiWorldTickCapacity` 는 그 구성을 그대로 재현한다.

```bash
cd Benchmark/x64/Release
./Benchmark.exe --benchmark_filter="BM_MultiWorldTickCapacity"
# 메모리를 볼 때는 구성 하나만 (앞 구성이 반납한 블록을 할당자가 재사용해 rss_delta 가 작게 나온다)
./Benchmark.exe --benchmark_filter="BM_MultiWorldTickCapacity/16/1/40000"
```

인자는 `(스레드 수, 스레드당 월드 수, 월드당 몬스터 수)`. 워커 스레드는 배리어 두 개로
동기화해서 **모두가 같은 틱을 동시에 도는** 벽시계 시간을 잰다. 동기화 없이 각자 돌게 두면
빠른 스레드가 앞서 나가면서 경쟁 상황이 실제보다 순해진다.

틱을 지키는지는 **가장 느린 스레드**가 정하므로, 매 틱 워커별 소요의 최댓값을 모아
`tick_ms`(그 평균)와 `worst_tick_ms`(그 최댓값)로 보고한다. 예산은 10Hz 기준 100ms.

### 먼저 고쳐야 했던 것 — lua 상태가 프로세스에 하나뿐이다

`GameMode::L_` 는 `static lua_State*` 다. 맵마다 게임 모드 객체는 따로지만 lua VM 은
프로세스 전체가 공유하고, `Map::UpdateGameMode` 가 **매 틱 맵마다** `on_update` / `check_end`
두 번을 그 VM 에서 호출한다. 월드를 스레드에 나눠 돌리는 순간 두 스레드가 같은 lua 스택을
동시에 밀고 당기게 된다.

이건 벤치마크만의 문제가 아니라 `world.thread_count > 1` 인 운영 구성이 그대로 안고 있던
경합이다. lua 진입점 전부를 `GameMode::luaMutex_`(recursive — `Update` 가 `End` 를 부른다)로
직렬화했다. 한 틱에 맵당 두 번뿐이라 비용은 측정에 잡히지 않는다. 몬스터 AI 는 lua 를 타지
않는다(`behaviortree_cpp`).

### 스레드 확장 — 월드당 20,000마리 고정

| 스레드 | 월드 | 몬스터(전체) | tick_ms | worst | 예산 대비 |
|---|---|---|---|---|---|
| 1 | 1 | 20,000 | 19.5 | 22.5 | 19.5% |
| 2 | 2 | 40,000 | 21.9 | 25.5 | 21.9% |
| 4 | 4 | 80,000 | 25.8 | 29.8 | 25.8% |
| 8 | 8 | 160,000 | 29.9 | 32.0 | 29.9% |
| 16 | 16 | 320,000 | 44.4 | 46.7 | 44.4% |

월드끼리는 게임 상태를 전혀 공유하지 않는데도 **공짜는 아니다**. 스레드를 16배로 늘리면
몬스터도 16배가 되지만 틱은 19.5ms → 44.4ms 로 2.3배가 된다. 락 경합이 아니라 메모리
대역폭과 캐시 경쟁이다 — navmesh 질의, BT 틱, 그리드 순회가 전부 포인터를 따라다니는
작업이라 코어를 늘려도 메모리 쪽이 먼저 막힌다. 그래도 **스루풋은 계속 오른다**
(16스레드에서 코어당 유효 처리량이 1스레드 대비 약 44%).

### 한계 지점 — 16스레드에서 밀도를 올린다

| 스레드 | 월드 | 월드당 | 몬스터(전체) | tick_ms | worst | 예산 대비 | RSS |
|---|---|---|---|---|---|---|---|
| 16 | 16 | 20,000 | 320,000 | 44.7 | 48.0 | 44.7% | 1.2 GB |
| 16 | 16 | 30,000 | 480,000 | 65.6 | 70.5 | 65.6% | 1.8 GB |
| 16 | 16 | 40,000 | **640,000** | 97.9 | 101.8 | **97.9%** | 2.6 GB |
| 16 | 32 | 20,000 | 640,000 | 90.1 | 94.5 | 90.1% | 3.1 GB |

**16코어(Ryzen 9 5950X) 한 프로세스에서 10Hz 를 지키는 상한은 약 60만 마리**다.
640,000 에서 평균 97.9%, 최악 101.8% 로 예산에 닿는다. 운영 여유(플레이어 부하, 네트워크
IO, GC 성 스파이크)를 감안하면 **48만 마리(65%) 근처가 실무 상한**이다.

### 같은 총량이라도 어디에 담느냐가 다르다

| 배치 | 몬스터(전체) | 예산 대비 |
|---|---|---|
| 8스레드 × 40,000 | 320,000 | 78.2% |
| 16스레드 × 20,000 | 320,000 | 44.7% |
| 16스레드 × 40,000 | 640,000 | 97.9% |
| 16스레드 × 월드2개 × 20,000 | 640,000 | 90.1% |

같은 320,000 을 8스레드에 40,000씩 담으면 78%, 16스레드에 20,000씩 담으면 45% 다.
스레드가 두 배인 것만으로는 설명이 안 되는 차이인데, **맵 하나에 몰린 밀도가 비용을
초선형으로 올리기 때문**이다(그리드 셀당 후보 수가 늘어 탐지 스캔이 길어진다).

같은 이유로 640,000 을 월드 16개에 40,000씩 담는 것(97.9%)보다 월드 32개에 20,000씩
나누는 편(90.1%)이 낫다. 대신 월드가 늘면 몬스터와 무관한 고정 메모리(월드마다 field 맵
전부의 navmesh + 그리드)가 붙어서 RSS 는 2.6GB → 3.1GB 로 올라간다.
**틱이 빠듯하면 월드를 쪼개고, 메모리가 빠듯하면 월드당 밀도를 올린다.**

### 콜드 스타트가 여전히 진짜 위험이다

`first_tick_ms` 는 스폰 직후 전원이 같은 틱에 배회 목적지를 잡고 경로를 계산하는 값이다.

| 구성 | first_tick_ms |
|---|---|
| 16스레드 × 20,000 (320k) | 1,334 |
| 16스레드 × 30,000 (480k) | 1,979 |
| 16스레드 × 40,000 (640k) | 2,647 |

정상 틱이 98ms 인 구성에서 **첫 틱은 2.6초**다. 기동 직후 한 번은 반드시 이만큼 멈춘다.
스폰을 여러 틱에 나눠 뿌리지 않는 한 이 스파이크는 남는다 — 13절에서 지적한 것과 같은
문제이고, 몬스터가 늘어난 만큼 그대로 커진다.

### 이 수치를 그대로 믿으면 안 되는 것

- **플레이어가 0명이다.** 4·8절에서 봤듯 교전이 붙으면 탐지가 매 틱 성공하면서 경로 재계산과
  사거리 raycast 가 붙는다. 실제 상한은 이보다 낮다.
- **네트워크 IO 가 없다.** 운영에서는 같은 워커 스레드가 `io_context::poll()` 도 돌린다.
  16스레드로 코어를 다 쓰면 IO 가 월드 틱과 코어를 다툰다.
- **`world.thread_count` 는 포트 개수를 넘지 못한다.** 16스레드를 쓰려면 실행 인자로 포트를
  16개 이상 열어야 한다(`ResolveWorkerCount` 가 서버 수로 상한을 건다).
- **RSS 는 구성 하나만 필터해서 돌렸을 때만 맞다.** 여러 구성을 이어 돌리면 할당자가 앞
  구성의 블록을 재사용해 `rss_delta_mb` 가 실제보다 작게 나온다.

## 17. 봇 동시접속 — 스레드를 늘려 가며 잰 실제 수용량

16절은 몬스터만 있는 월드를 스레드에 나눠 돌렸을 때의 한계였다. 여기서는 **실제 서버를 띄우고
실제 프로토콜로 봇을 접속시켜** 잰다. 로그인 → 스폰 → AoI 동기화 → 전투까지 전부 도는 상태다.

측정 환경: Release x64, Ryzen 9 5950X(16C/32T), 서버와 봇이 **같은 기계**, 루프백.
월드 하나 = 포트 하나 = 스레드 하나(`world.thread_count`), 월드마다 맵 6개 + 몬스터 330마리.

```powershell
# 서버 — 포트 개수가 곧 월드 개수이고, world.thread_count 는 그보다 많아질 수 없다
x64\Release\Game.exe 65001 65002 ... 65016 --config <server_config.json>

# 봇 — 포트들에 봇 번호로 나눠 붙는다(--ports 는 이번에 추가했다)
Bot\x64\Release\Bot.exe --ports 65001-65016 --bots 3200 --threads 12 --duration 90 --rampup 250 --quest off
```

### 서버가 스스로 재게 만들었다 — `[tick]` 로그

봇이 재는 왕복 지연에는 네트워크와 클라 틱이 섞여 있어서, 느려졌을 때 **월드가 밀린 것인지
그 앞뒤가 밀린 것인지** 구분하지 못한다. 그래서 워커 루프(`ServerManager::RunWorker`)가
5초마다 자기 프레임을 요약하게 했다.

```text
[tick] worker=0 servers=1 sess=400 | frame avg 5.89 max 112.20 ms over16 43/201 (40 fps)
                                   | sim avg 17.81 max 22.61 ms over100 0/50 late 0 drop 0
```

예산이 둘이라 따로 센다. 프레임 루프는 16ms 주기이고 월드 시뮬레이션은 그 안에서 10Hz다.

| 항목 | 뜻 |
| --- | --- |
| `frame` / `over16` | 프레임 하나(IO 폴링 + 게임 로직)의 시간과 16ms 초과 횟수 |
| `sim` / `over100` | 월드를 실제로 돌린 프레임의 로직 시간과 100ms 예산 초과 횟수 |
| `late` | 한 프레임에서 10Hz 틱을 두 번 이상 따라잡아야 했던 횟수 — **이미 밀린 상태다** |
| `drop` | 따라잡기 상한(5틱)을 넘겨 시뮬레이션을 통째로 버린 횟수 |

통계는 워커 스레드의 지역 변수다. 재는 것 때문에 스레드 사이에 새 공유 상태가 생기지 않는다.

### 먼저 고쳐야 했던 것 #1 — 파티 상태가 프로세스에 하나뿐이었다

8스레드에 봇 3200명을 붙이면 **서버가 매번 죽었다**(로그가 문장 중간에서 끊겼다).
원인은 `PartyManager::Instance()` 와 `PlayerParty::registry()` 가 프로세스 전역 싱글턴이라는
것이었다. 이 둘은 로그인/로그아웃마다 해시맵에 삽입·삭제를 한다. 월드를 여러 스레드에서
돌리면 워커들이 같은 맵을 동시에 고친다.

`static` → `static thread_local` 로 바꿨다. 월드는 정확히 하나의 워커 스레드에 묶이므로
스레드 지역이면 곧 월드 지역이고, 잠금이 하나도 필요 없다. 의미로도 그게 맞다 —
다른 포트(월드)의 플레이어끼리는 서로 보이지도 않으니 같은 파티일 수 없다.

같은 자리에서 `Player` 의 런타임 id 카운터도 고쳤다(`static long` → `std::atomic<long>`).
그냥 `++` 로 두면 두 스레드가 같은 번호를 받아 가는데, 그 번호가 파티 색인의 키다.

이건 벤치마크만의 문제가 아니라 **`world.thread_count > 1` 로 띄운 서버가 이미 안고 있던
결함**이다. 16절의 lua 상태와 같은 종류이고, 이번엔 실제로 죽는 것으로 드러났다.

> 참고: 이 크래시는 로그를 줄이자 비로소 나타났다. 로그가 켜져 있을 때는 콘솔 싱크의
> 뮤텍스가 워커들을 줄 세워서 경합 구간이 좁혀졌기 때문이다. **잠금이 아닌 것이 잠금 역할을
> 하고 있으면, 그것을 걷어내는 순간 죽는다.**

### 먼저 고쳐야 했던 것 #2 — 로그가 프레임을 붙잡고 있었다

3200명 구성에서 서버가 **초당 2,800줄**을 뱉고 있었다. 대부분은 `move target actor id ...`
— 이동 패킷마다 한 줄이다. 로그는 두 싱크(콘솔 + 파일)에 동기로 쓰이고 콘솔 싱크는
모든 워커가 공유한다. 프레임이 수백 ms 씩 멈추던 구간의 상당 부분이 이것이었다.

- 콘솔 싱크를 `stdout_sink_st` → `stdout_sink_mt` 로 바꿨다. 월드가 여러 스레드에서
  도는 이상 `_st` 싱크는 출력이 섞이는 정도가 아니라 내부 상태가 깨진다.
- 설정에 `log.level` 을 넣었다(기본 `debug` — 기존 동작 그대로). 아래 측정은 전부
  `info` 로 돌렸다. 그것만으로 초당 2,800줄이 120줄로 떨어진다.

### 스레드를 늘리면 그만큼 받는다 — 월드당 200명 고정

| 스레드=월드 | 총 봇 | 월드당 sim avg | ping p95 | p99 | max | 서버→클라 |
|---|---|---|---|---|---|---|
| 1 | 200 | 4.4 ms | 32 | 36 | 53 ms | 9.5 MB/s |
| 2 | 400 | 4.5 ms | 32 | 40 | 104 ms | 19.5 MB/s |
| 4 | 800 | 5.3 ms | 32 | 39 | 94 ms | 39.6 MB/s |
| 8 | 1600 | 7.8 ms | 32 | 42 | 138 ms | 80.2 MB/s |
| 16 | 3200 | 13.8 ms | 32 | 57 | 469 ms | 167.7 MB/s |

봇 수는 스레드에 비례해 늘고 지연은 거의 그대로다. 다만 **월드당 틱 비용이 같은 인원에도
3배로 오른다**(4.4 → 13.8ms). 스레드가 코어를 다 채우면서 메모리 대역과 캐시를 다투기
때문이고, 여기에는 같은 기계에서 도는 봇 프로세스도 한몫한다.
16스레드 3200명에서 서버가 2.74코어, 봇이 1.26코어를 썼다 — CPU 는 남는다.

### 월드 하나에는 몇 명까지 — 1스레드/1포트

| 월드 인원 | sim avg | frame max | ping p95 | p99 | max | 서버→클라 |
|---|---|---|---|---|---|---|
| 200 | 4.4 ms | 81 ms | 32 | 36 | 53 ms | 9.5 MB/s |
| 400 | 8.4 ms | 182 ms | 32 | 42 | 149 ms | 41.3 MB/s |
| 800 | 18.9 ms | **964 ms** | 79 | **606** | 841 ms | 162.1 MB/s |

**시뮬레이션은 끝까지 예산의 20%도 못 채운다.** 800명에서 무너지는 것은 틱이 아니라
프레임이다 — 로직이 19ms 인데 프레임이 964ms 걸리고 `drop` 이 뜬다. 그 시간은 IO 폴링,
곧 800개 세션에 대한 송신 처리에서 나온다.

이유는 데이터에 있다. 모든 맵의 `aoi_radius` 가 0 이라 **관심영역이 꺼져 있고**(11절),
서버는 브로드캐스트 모드로 돈다. 봇이 재는 `view` 값이 그것을 그대로 보여 준다 —
200명이면 213, 800명이면 813, 즉 **전원이 전원을 본다**. 트래픽이 인원의 제곱으로 는다.
9.5 → 41 → 162 MB/s 가 정확히 그 곡선이다.

18절의 AI 재구성 뒤 같은 구성을 다시 쟀다. 서버 `x64\Release\Game.exe 65001`(포트 1개 =
월드 1개 = 스레드 1개, `log.level=info`), 봇
`Bot.exe --port 65001 --bots N --threads 8 --duration 90 --rampup 50 --quest off`,
구성마다 서버를 새로 띄웠다. 월드에는 맵 6개와 몬스터 330마리가 있다.

### 월드 틱은 이제 병목 근처에도 없다

유휴(플레이어 0명, 몬스터 330마리, 맵 6개) `sim` 이 **0.9ms** 다. 여기서 인원을 늘려 가며
플레이어 한 명이 틱에 더하는 비용을 빼 보면 이렇게 된다.

| 인원 | sim | 인원분(sim - 0.9) | 1인당 |
|---|---|---|---|
| 200 | 6.1 ms | 5.2 ms | 26 us |
| 400 | 11.0 ms | 10.1 ms | 25 us |
| 600 | 17.4 ms | 16.5 ms | 28 us |
| 800 | 25.2 ms | 24.3 ms | 30 us |
| 1,000 | 32.0 ms | 31.1 ms | 31 us |

**틱 비용은 사실상 전부 플레이어분이다.** 몬스터 330마리 AI 는 0.9ms 안에 들어가고,
1,000명 구성에서도 `sim` 은 예산(100ms)의 32% 에 그친다. `over100` 은 끝까지 0 이었다.
1인당 비용이 26 → 31us 로 완만히 오르는 것은 브로드캐스트(모두가 모두를 본다) 때문이다.

무너지는 곳은 프레임이다. 800명에서 `sim` 25ms 인데 `frame max` 1,540ms 이고 `drop` 이 뜬다.
그 시간은 IO 폴링 — 세션 수만큼의 송신 처리에서 나온다. 17절의 결론과 같고, 이번에는
월드 틱 쪽 여유가 훨씬 커진 만큼 **남은 비용이 전부 송신 경로에 있다는 것이 더 분명해졌다.**

### 무엇이 비싼가 — 송신 한 방향, 그리고 패킷 크기

"패킷 송수신이 비싸다" 는 두 군데를 좁혀야 맞다. 봇이 주고받은 양을 보면 방향이 갈린다.

| 봇 | 클라→서버 | 서버→클라 | 비율 |
|---|---|---|---|
| 200 | 1.7 MB | 758.5 MB | 446배 |
| 400 | 2.9 MB | 3,283.3 MB | 1,132배 |
| 600 | 4.3 MB | 7,217.4 MB | 1,678배 |
| 800 | 5.5 MB | 11,613.8 MB | 2,112배 |
| 1,000 | 6.7 MB | 17,113.9 MB | **2,554배** |

1,000명이 90초 동안 서버로 올린 것이 6.7MB 다. **수신 경로는 병목 후보가 아니다.**

그리고 문제는 패킷 '개수' 가 아니라 '크기' 다.

| 봇 | 1인당 수신 pps | 패킷 1개 평균 |
|---|---|---|
| 200 | 21.2 | 1.9 KB |
| 400 | 16.1 | 5.7 KB |
| 600 | 16.2 | 8.3 KB |
| 800 | 16.9 | 9.5 KB |
| 1,000 | 15.9 | **12.0 KB** |

1인당 패킷 수는 초당 16개로 거의 일정하다(10Hz 틱 + 알파). 소켓 호출 횟수나 프로토콜
오버헤드가 아니라 **한 번에 싣는 액터 수가 인원에 비례해 늘어난다.** 모든 맵의
`aoi_radius` 가 0 이라 맵의 모든 액터를 모든 플레이어에게 보내기 때문이고, 그래서
1인당 대역이 42 → 91 → 134 → 161 → 190 KB/s 로 인원에 비례하고 총량은 인원² 이 된다.

액터 하나당 약 12바이트로 이미 조밀하다(`ActorInfo` — 위치 + 변경분만). 즉 **줄일 수 있는
것은 인코딩이 아니라 "누구에게 무엇을 보내는가" 뿐이다.**

### 그 비용이 앉는 자리는 두 곳이다

송신 버퍼는 세션마다 복사되지 않는다 — `SendBroadcastState` 가 메시지를 한 번 만들고
`GameSession::Send` 는 `shared_ptr` 를 큐에 넣을 뿐이다. 그런데도 비용은 인원에 비례한다.

- **`sim` 안** — 세션마다 `DoWrite()` 가 그 자리에서 `async_write` 를 걸어 12KB 를 커널로
  넘긴다. 이 호출이 월드 틱 안에서 일어나므로 1인당 26~31us 가 `sim` 에 그대로 들어간다.
- **`frame` 안** — 완료 처리와 나머지 IO 폴링. 800명 이상에서 1,400~1,500ms 스파이크와
  `drop` 이 나는 곳이다.

그래서 결론은 "송수신이 비싸다" 가 아니라 **"보낼 필요 없는 것을 보내고 있다"** 이다.
고칠 곳은 네트워크 계층(버퍼/배치/프로토콜)이 아니라 보낼 양 자체이고, 그것이 관심영역이다.

### 그래서 계측을 넣었다

11·13절이 "AoI 를 평가하려면 틱마다 나가는 바이트를 세야 한다" 로 미뤄 둔 것을 넣었다.
`GameSession::Send` 가 실제로 큐에 넣은 메시지와 바이트를 **thread_local** 로 세고
(월드는 워커 스레드에 고정되므로 워커별 집계이고, 스레드 사이에 새 공유 상태가 생기지 않는다)
`[tick]` 줄이 그것을 함께 남긴다.

```text
[tick] worker=0 ... late 0 drop 0 | out 36.4 MB/s 6435 msg/s avg 5931 B
```

이제 AoI 를 켰을 때 무엇이 줄었는지 봇이 받은 바이트로 역산하지 않고 서버에서 바로 본다.

### 그래서 한 월드에 몇 명인가

| 기준 | 답 |
|---|---|
| 입장/유지가 되는가 | **1,000명도 된다** (실패·끊김 0) |
| 월드 틱 예산(sim < 100ms) | 1,000명에서도 32% — **닿지 않는다** |
| 체감 가능한 지연(p99 < 250ms, drop 0) | **약 400명** |
| p95 가 무너지는 지점 | 600명(138ms)부터, 800명(472ms)에서 확실히 |

> **측정 조건 주의**: 이번 측정은 같은 기계에서 IDE(약 2.9GB) · 브라우저 · 설치 프로그램이
> 함께 도는 상태로 잰 값이다. 그래서 꼬리 지연(p99/max)과 `frame max` 의 절대값은 위
> 표(조용한 기계에서 잰 200명 p99 36ms / 800명 606ms)와 직접 비교하면 안 된다.
> **스윕 안의 다섯 구성은 조건이 같으므로 서로 비교할 수 있고**, 유휴 0.9ms 와 1인당
> 26~31us 도 그 안에서 나온 값이다. AI 교체 전후를 지연으로 비교하려면 조용한 기계에서
> 두 바이너리를 다시 재야 한다.

### 같은 인원이라도 어디에 담느냐가 다르다

| 배치 | 총 봇 | sim avg / max | over100 | late / drop | p95 / p99 | 서버→클라 |
|---|---|---|---|---|---|---|
| 16스레드 × 200 | 3,200 | 13.9 / 24.2 ms | 0 | 2 / 0 | 32 / 57 ms | 168 MB/s |
| 8스레드 × 400 | 3,200 | 17.6 / 28.5 ms | 0 | 20 / 3 | 38 / 220 ms | 315 MB/s |
| 16스레드 × 300 | 4,800 | 14.7 / 205.1 ms | 1 | 24 / 0 | 58 / 339 ms | 359 MB/s |
| 16스레드 × 400 | 6,400 | 21.5 / 63.5 ms | 0 | 65 / 15 | 239 / 742 ms | 590 MB/s |

같은 3,200명인데 월드 16개에 200명씩 담으면 p99 가 57ms, 월드 8개에 400명씩 담으면
220ms 다. 16절의 몬스터와 똑같은 결론이다 — **밀도가 비용을 초선형으로 올린다.**
다만 원인은 다르다. 몬스터는 그리드 탐지 스캔이었고, 여기서는 브로드캐스트 대역이다.

### 그래서 몇 명인가

| 기준 | 답 |
|---|---|
| 월드 틱 예산(sim < 100ms) | **한 번도 닿지 않는다.** 6,400명에서도 21ms(21%)다 |
| 체감 가능한 지연(p99 < 100ms, drop 0) | **3,200명** (16스레드 × 200) |
| 무너지는 지점 | 4,800명부터 `over100` 과 p99 300ms 대가 나오고, 6,400명은 p99 742ms |
| 스레드를 더 늘리면 | 물리 코어 수까지는 값을 한다. 6,400명은 스레드가 아니라 기계의 한계다 — 아래 참조 |
| 월드 하나 | **200~400명**. 800명은 브로드캐스트만으로 162MB/s 를 쓰며 무너진다 |

퀘스트 시나리오를 켜고(`--quest on`) 같은 16스레드 × 200 = 3,200명을 120초 돌린 결과도
같다 — p95 34 / p99 74ms, sim 11.9ms, `drop` 0, 퀘스트 1,603건 수락. 맵 이동과 DB 쓰기가
섞여도 수용량은 변하지 않았다(오히려 봇이 6개 맵으로 흩어져 대역은 90MB/s 로 줄었다).

### 스레드를 더 늘리면 6,400명을 넘길 수 있나

같은 인원을 더 많은 월드에 나눠 담아 봤다. 월드가 늘면 월드당 인원이 줄고, 브로드캐스트는
인원의 제곱이므로 대역이 크게 준다. 실제로 그렇게 된다.

| 총 봇 | 배치 | 서버→클라 | 월드당 sim | late / drop | ping p95 / p99 | 서버 CPU |
|---|---|---|---|---|---|---|
| 3,200 | 16 × 200 | 168 MB/s | 13.9 ms | 2 / 0 | 32 / 57 ms | 2.74 |
| 3,200 | **32 × 100** | 86 MB/s | 20.3 ms | 0 / 0 | 32 / **45** ms | 6.56 |
| 4,800 | 16 × 300 | 359 MB/s | 14.7 ms | 24 / 0 | 58 / 339 ms | — |
| 4,800 | **24 × 200** | 248 MB/s | 18.1 ms | 12 / 1 | 54 / **237** ms | 6.52 |
| 6,400 | 16 × 400 | 590 MB/s | 21.6 ms | 61 / 14 | 239 / 742 ms | 5.23 |
| 6,400 | **32 × 200** | 322 MB/s | 12.5 ms | **17 / 0** | 323 / **752** ms | 9.17 |

읽는 방법이 둘로 갈린다.

**서버 안쪽은 확실히 좋아진다.** 6,400명을 월드 32개에 담으면 대역이 절반이 되고, 버려지는
시뮬레이션 틱이 14 → 0 으로 사라지며, 월드당 틱 시간도 21.6 → 12.5ms 로 떨어진다.
월드 틱만 보면 32스레드 6,400명은 건강하다.

**그런데 클라가 느끼는 지연은 그대로다**(p99 742 → 752ms). 서버의 월드 루프가 멀쩡한데
왕복 지연이 그대로라는 것은, **6,400명 구간의 지연이 더 이상 월드 틱에서 나오지 않는다**는
뜻이다. 남는 곳은 송수신 경로와 그 아래(루프백, 그리고 같은 기계에서 도는 봇 프로세스)다.
그 시점에 서버 9.2코어 + 봇 2.8코어로 물리 16코어 중 12개를 쓰고 있었다.

**그리고 월드를 쪼개는 것은 공짜가 아니다.** 같은 3,200명인데 월드 16개면 2.74코어,
32개면 6.56코어다 — 인원은 그대로인데 CPU 가 2.4배다. 월드마다 맵 6개와 몬스터 330마리가
딸려 오기 때문이다. 아무도 없는 월드는 거의 공짜지만(32월드 유휴 = 0.28코어) 플레이어가
들어오는 순간 그 몬스터들이 전부 교전에 들어간다. 월드 32개면 몬스터도 10,560마리다.

정리하면 **스레드는 물리 코어 수까지는 값을 하고, 그 위로는 아니다.** 6,400명은
`world.thread_count` 의 한계가 아니라 이 기계의 한계다. 넘기려면 순서가 있다.

1. **부하 생성기를 다른 기계로 뺀다.** 지금은 봇이 2~3코어와 300~600MB/s 를 같이 쓴다.
   이것만으로 측정 상한이 올라간다(실제 수용량이 얼마인지는 그때 다시 재야 안다).
2. **브로드캐스트를 없앤다.** 모든 맵이 `aoi_radius = 0` 이라 전원이 전원을 본다.
   비용의 뿌리가 여기다.
3. **월드당 몬스터를 줄인다.** 월드를 잘게 쪼개는 전략의 발목을 잡는 것이 이 고정 비용이다.

> 2번은 이번에 검증하지 못했다. AoI 를 켜려면 봇이 맵에 흩어져야 하는데(다 같이 한자리에
> 모여 있으면 반경을 얼마로 잡든 전원이 서로의 시야에 있다), `ai.wander_radius` 를 넓혀
> 흩뿌렸더니 봇이 6,400명 중 6,386명이 죽은 채로 남아 부하 자체가 성립하지 않았다.
> 흩어진 봇이 왜 전멸하는지는 따로 볼 문제다. **그래서 AoI 를 켰을 때의 수용량은 미측정이다.**

### 이 수치를 그대로 믿으면 안 되는 것

- **봇과 서버가 같은 기계에서 돈다.** 6,400명 구간에서 서버 5.2코어 + 봇 3.4코어를 썼다.
  16코어 중 절반이라 CPU 자체는 남지만, 590MB/s 를 주고받는 루프백 비용은 양쪽에 다 든다.
  실제 NIC 라면 그 전에 대역이 먼저 끝난다 — 590MB/s 는 4.7Gbps 다.
- **봇 전원이 한 맵의 스폰 지점 20m 안에 모여 있다.** `--quest off` 면 봇은 스폰 주변만
  배회한다. 관심영역을 켜도(AoI) 이 배치에서는 아무것도 줄지 않는다. 즉 이 표는
  **"전원이 한자리에 모인" 최악의 경우**이고, 흩어진 상태의 수용량은 이보다 높다.
- **`aoi_radius` 가 0 이라 브로드캐스트다.** 위 한계는 대부분 이것이 정한다. 인원을
  더 받고 싶으면 스레드보다 먼저 **관심영역을 켜는 것**이 답이다(11·12절).
- **`world.thread_count` 는 포트 개수를 넘지 못한다.** 16스레드를 쓰려면 포트를 16개
  열어야 한다. 봇도 `--ports 65001-65016` 으로 나눠 붙여야 한다 — 한 포트에 몰면
  스레드를 아무리 늘려도 월드 하나만 돈다.
- **DB 는 계정 생성까지 포함해 측정에 들어 있다.** 봇은 실행마다 새 계정을 만든다.

## 18. 조치 #9 — 몬스터 AI 를 ECS 로 재구성

14절이 "actors 가 59% 이고 이제 프레임워크가 아니라 노드 안의 실제 작업" 이라고 적었는데,
그 진단이 반만 맞았다. 비싼 것은 노드의 일이 아니라 **모든 몬스터가 매 틱 트리를 처음부터
끝까지 타고 내려간다는 구조 자체**였다.

기존 두 백엔드는 몬스터 한 마리마다 노드 객체 13개를 힙에 만들고, 매 틱 그 트리를 가상
호출로 순회하며, 노드마다 `Monster` 객체를 다시 만지고, 조건이 실패해도 그 사실을 알기까지
같은 경로를 다 지나간다. 트리 구조는 모든 몬스터가 똑같은데 마리 수만큼 복제된다.

### 무엇을 바꿨나

[MonsterAISystem](../Engine/AI/MonsterAISystem.h) 을 세 번째 백엔드(`BTBackend::Ecs`)로 넣고
**기본값으로 삼았다.** 트리를 "타고 내려가지" 않는다 — 이 트리는 Fallback 하나에 조건이 셋뿐이라
조건 비트에서 행동으로 가는 **표 하나로 컴파일된다.**

| 조건 비트 | 행동 |
|---|---|
| `!Alive` | Dead |
| `Alive` | Patrol |
| `Alive + HasTarget` | Chase |
| `Alive + HasTarget + InAttackRange` | Attack |

그래서 한 틱은 순회가 아니라 **동종 작업의 배치 패스** 몇 개로 끝난다.

```
1) 스케줄 스캔  4바이트 배열만 훑어 이번 틱에 사고할 개체를 고른다
2) 조건 평가    생존 → (생존한 것만) 탐지 → (교전 중인 것만) 사거리
                비싼 조건일수록 더 좁은 무리에만 돈다
3) 결정         조건 비트로 표를 찾아 행동별 버킷에 담는다(분기 없음)
4) 실행         버킷마다 한 가지 일만 하는 루프 — 배회 / 추격 / 공격 / 사망
```

버킷이 곧 의도(intent) 목록이고, 4)의 각 루프가 그 의도를 실행하는 시스템이다. 결정과 실행이
갈라져 있어서 트리는 세계를 직접 만지지 않는다.

성능의 근거가 되는 선택은 넷이다.

1. **컴포넌트를 뜨거운 것과 차가운 것으로 쪼갰다.** 매 틱 전수 순회하는 것은 4바이트짜리
   `AIScheduleComponent` 배열뿐이다(40,000마리라도 160KB). 사고할 차례가 된 개체만 64바이트
   `AIAgentComponent` 를 만진다.
2. **배회 중에는 10틱에 한 번만 사고한다.** 예전에도 가장 비싼 적 탐지 스캔은 `DetectEnemy`
   노드가 스스로 10틱마다로 걸렀지만, 나머지 노드는 매 틱 다 돌았다. 이제 그 주기가 사고
   전체의 주기다 — **스캔 간격은 예전과 같고 나머지가 함께 사라진다.** 교전 중이거나 사망
   처리 중이면 예전처럼 매 틱 사고하고, 피격은 `Monster::WakeAI` 가 즉시 깨운다.
3. **벽시계를 버렸다.** 휴식/이동 타임아웃/소멸 지연이 전부 시뮬레이션 시간(float 초) 비교다.
   `steady_clock::now()` 는 윈도우에서 QPC 라 마리마다 부르면 그대로 틱 비용이 되고,
   무엇보다 시간이 dt 와 무관해져 테스트가 벽시계에 의존하게 된다.
4. **상태는 바뀔 때만 쓴다.** `Actor::SetState` 는 ECS 컴포넌트를 엔티티 해시로 찾아 쓴다.
   예전 트리는 배회 중에도 매 틱 `SetState(Patrol)` 을 불러 그 해시 조회를 지불했다.

노드 로직을 공유하던 `MonsterBTNodes.h` 는 그대로 두었다 — 기존 두 백엔드는 손대지 않았고
이 백엔드만 조건/행동을 배치 형태로 따로 구현한다. 세 백엔드가 같은 결정을 내리는지는
[MonsterBTTest](../UnitTest/MonsterBTTest.cpp) 가 같은 시나리오를 셋으로 각각 돌려 고정하고,
ECS 쪽 고유 성질(결정표·개체별 상태·스케줄·피격 즉시 반응·소멸 지연)은
[MonsterAISystemTest](../UnitTest/MonsterAISystemTest.cpp) 가 본다.

### actors 단계 — 백엔드만 바꾼 직접 비교

```bash
./Benchmark.exe --benchmark_filter="BM_BTWorldTickActors" --benchmark_min_time=2.0
```

|---|---|---|---|

인하우스 BT 대비 **3.3배**, behaviortree_cpp 대비 78배다.

### 월드 전체 — 좁은 맵(primary)

`BM_BTCapacityEngaged` 는 백엔드를 스폰 전에 고정해 두 구현을 한 번의 실행으로 비교한다.

| 구성 | CodeBase | **Ecs** | 변화 |
|---|---|---|---|
| 10,000 배회만 | 3.78 ms | **2.66 ms** | -30% |
| 40,000 배회만 | 40.2 ms | **25.0 ms** | -38% |
| 10,000 + 플레이어 50 | 5.61 ms | **0.759 ms** | -86% |
| 20,000 + 플레이어 50 | 26.3 ms | **11.9 ms** | -55% |
| 40,000 + 플레이어 50 | 59.7 ms | **40.2 ms** | -33% |

교전이 붙은 쪽의 이득이 훨씬 크다. 예전에는 몬스터가 교전 중이면 **전원이** 매 틱 트리를
다 돌았지만, 이제 매 틱 도는 것은 실제로 타깃을 잡은 개체뿐이다.

> 교전 구성(0.759ms)이 배회 전용(2.66ms)보다 싼 것은 오타가 아니다. 이 맵은 좁아서
> 플레이어 50명이 있으면 대부분의 몬스터가 교전에 들어가고, **교전 중인 몬스터는 배회
> 목적지를 새로 내지 않는다.** 지금 배회 전용 구성에서 제일 비싼 것은 AI 가 아니라
> `INavMovement::Patrol`(임의 지점 + 경로 산출, 1회 9.5us)이다.

### 월드 전체 — 큰 맵(Arcadia Plains 500×500, 실제 분포)

13절과 같은 조건이다 — navmesh 전체에 면적 비례로 흩뿌리고, 플레이어는 `Map::Enter` 까지
거쳐 직렬화·전송 단계가 실제로 돈다.

```bash

```

| 10,000 | 9.59 ms (9.6%) | **5.86 ms (5.9%)** | -39% |

**10Hz 예산 기준 한 스레드 수용량이 약 55,000마리 → 약 110,000마리가 됐다.**

### 콜드 스타트가 5배 줄었다

13절과 16절이 "기동 직후 수 초의 스톨" 로 지적한 값이다(`first_tick_ms` — 스폰 직후 첫 틱).

| 몬스터 | CodeBase | **Ecs** |
|---|---|---|
| 10,000 | 535 ms | **103 ms** |
| 20,000 | 1,020 ms | **206 ms** |
| 40,000 | 2,077 ms | **408 ms** |
| 60,000 | 3,096 ms | **634 ms** |
| 100,000 | — | 1,041 ms |

의도한 것은 아니고 사고 스케줄의 부산물이다. 예전에는 스폰된 전원이 **같은 틱에** 배회
목적지를 잡아 경로를 계산했는데, 이제 첫 사고 시점이 `actorId % 10` 으로 흩어져 그 비용이
10틱에 나뉜다. 근본 해결(스폰 자체를 여러 틱에 나누기)은 그대로 남아 있다.

### 대가와 남은 것

- **BT 디버그 뷰어를 쓸 수 없다.** 뷰어(`BTDebugManager`)는 behaviortree_cpp 트리에만 붙는다.
  필요하면 몬스터 스폰 **전에** `Monster::btBackend_ = BTBackend::BTCpp` 로 되돌린다.
- **트리 구조를 바꾸려면 결정표도 함께 고쳐야 한다.** 조건이 하나 늘면 표가 두 배가 된다
  (지금은 3비트/8칸). 조건 열 개짜리 트리라면 이 방식이 맞지 않는다 — 그때는 표 대신
  우선순위 규칙 목록을 훑는 편이 낫고, 그 경우에도 배치 패스 구조는 그대로 쓸 수 있다.
- **반응 지연이 최대 9틱 늘어난 자리가 하나 있다.** 배회 중 목적지 도달 판정이다.
  탐지·공격·사망은 예전과 같은 주기이거나 더 빠르다.
- **매 틱 전수 순회가 완전히 사라진 것은 아니다.** 스케줄 배열은 여전히 O(마리 수)다.
  링 버킷으로 O(사고하는 수)로 줄일 수 있지만, 컴포넌트 배열이 swap-erase 로 인덱스를
  재배치해서 버킷에 담아 둔 인덱스가 상해 버린다. 지금 비용(40,000마리에 160KB 순차 읽기)이
  작아서 미뤘다.
- **이제 배회 전용 구성의 병목은 AI 가 아니라 경로 산출이다**(`INavMovement::Patrol`, 9.5us).
  다음에 손댈 곳은 여기다.

> 측정 주의: 표의 두 백엔드는 **같은 실행 안에서** 잰 값이라 서로 비교할 수 있다.
> 실행을 나누면 큰 마리 수에서 ±30% 까지 흔들린다(40,000마리 ecs 를 다른 실행에서 재면
> 23.6ms / 34.3ms 가 나온다). 절대값보다 같은 실행 안의 비율로 읽을 것.

## 19. 조치 #10 — 관심영역을 인구로 켜고 끈다

17절의 재측정이 남긴 결론은 "무너지는 것은 월드 틱이 아니라 보내는 양" 이었다. 그래서
관심영역(AoI)을 실제 봇 부하에서 A/B 했다. 11절이 AoI 를 부정적으로 평가한 벤치는
시야 반경이 맵보다 커서 아무것도 걸러지지 않는 조건이었는데, 봇은 스폰 15m 안에서
배회하므로(`ai.wander_radius`) 반경 5~10 이면 실제로 걸러진다.

측정: 맵 1(Starting Village), 1포트/1스레드, 60초, `--quest off`.

| 구성 | sim avg | frame max | drop | ping p95 / p99 / max | 서버 송신 | 패킷 평균 |
|---|---|---|---|---|---|---|
| 400명 · 끔 | 10.9 ms | 198 ms | 0 | 32 / **73** / 198 ms | 38~42 MB/s | 9,140 B |
| 400명 · 반경 10 | 10.6 ms | 74 ms | 0 | 60 / 240 / 457 ms | 0.8~2.7 MB/s | 163~452 B |
| 400명 · 반경 5 | 10.4 ms | 139 ms | 0 | 50 / 97 / 234 ms | 0.9~2.8 MB/s | 173~327 B |
| 600명 · 끔 | 17.5 ms | 541 ms | 0 | 67 / **291** / 440 ms | 80~90 MB/s | 13,682 B |
| 600명 · 반경 5 | 15.9 ms | 517 ms | 0 | 212 / 438 / 668 ms | 2.6~7.1 MB/s | 247~418 B |
| 800명 · 끔 | 19.7 ms | **1,563 ms** | **1** | 193 / **866** / 1,093 ms | 125~155 MB/s | 18,119 B |
| 800명 · 반경 5 | 17.5 ms | **351 ms** | **0** | 245 / **484** / 643 ms | 5.8~14 MB/s | 320~1,313 B |

### 어느 쪽이 싼지는 인구가 정한다

**대역은 언제나 AoI 가 압도적으로 싸다** — 15~40배다. 그런데 지연은 인구에 따라 갈린다.

| 인원 | 끔(p99) | 반경 5(p99) | 이긴 쪽 |
|---|---|---|---|
| 400 | 73 ms | 97 ms | 끔 |
| 600 | 291 ms | 438 ms | 끔 |
| 800 | **866 ms** | **484 ms** | **AoI** |

브로드캐스트의 p99 는 73 → 291 → 866 으로 폭발하고 AoI 는 97 → 438 → 484 로 완만하다.
**교차점은 600~800명 사이다.**

이유는 둘의 비용 구조가 다르기 때문이다.

- 브로드캐스트는 메시지를 **한 번** 만들어 전원이 같은 버퍼를 공유한다(`shared_ptr`).
  그래서 사람이 적으면 싸지만, 한 사람에게 보내는 크기가 인원에 비례해 커진다.
- AoI 는 뷰어마다 메시지를 따로 만든다. 그래서 사람이 적으면 손해지만, 보내는 양이
  '전원 × 전원' 에서 '시야 안 × 그 자리를 보는 사람' 으로 떨어진다.

`sim` 은 어느 쪽이든 거의 같았다(15.9~19.7ms). **11절이 우려한 "뷰어별 조립 때문에 CPU 가
는다" 는 이 부하에서 나타나지 않았다** — 뷰어별로 직렬화하는 액터 수가 그만큼 적어져서
전체 직렬화 작업량이 상쇄된다.

### 그래서 데이터로 고정하지 않고 인구로 바꾼다

한쪽으로 고정하면 어느 구간에서든 한 번은 손해를 본다. [Map::UpdateAoIMode](../Engine/Map/Map.cpp) 가
플레이어가 들어오고 나갈 때마다 인구를 보고 모드를 바꾼다.

```
맵 데이터 aoi_radius > 0   "이 맵은 이 반경으로 쓸 수 있다"
플레이어 700명 이상        -> 관심영역
플레이어 600명 미만        -> 브로드캐스트   (경계에서 오가지 않게 벌려 둔다)
```

`aoi_radius` 가 0 인 맵은 인구와 무관하게 브로드캐스트다. `SetAoIRadius`(테스트/벤치의
강제 켬)는 인구를 무시하고 그대로 켠다 — 소수의 플레이어로 동작을 재현하는 통로다.

**끌 때 한 가지를 더 해야 한다.** 구독을 걷어내는 것만으로는 부족하다. AoI 에 걸러져
클라이언트가 아직 모르는 액터가 있는데 브로드캐스트는 '이번 틱에 바뀐 것' 만 보내므로,
가만히 있는 액터(정지한 NPC, 휴식 중인 몬스터)는 영영 전달되지 않는다. 그래서 전환 시
모든 액터를 변경됨으로 세워 다음 한 틱을 전체 스냅샷으로 만든다.
켤 때는 반대로 `SubscribeViewer(sendSnapshot=true)` 가 뷰어마다 스냅샷을 큐잉하므로,
전환 직후 한 틱만 브로드캐스트 한 틱과 같은 양이 나가고 그 뒤로 줄어든다.

규칙은 [AreaOfInterestTest](../UnitTest/AreaOfInterestTest.cpp) 의 `AoIModeSwitchTest` 가
고정한다(켜지는 인구, 히스테리시스 구간, 반경 없는 맵, 끌 때의 전체 스냅샷 예약).

### 실부하에서 전환을 확인했다

맵 1 에 반경 5 를 넣고 봇 800명을 램프업으로 붙였다(75초).

```text
11:16:00  Map 1 관심영역 켬 (플레이어 700명, 반경 5.0)
11:17:01  Map 1 관심영역 끔 (플레이어 599명)
```

켜는 값(700)과 끄는 값(599 — 600 미만)에서 정확히 한 번씩 바뀌었고, 그 사이 오가지 않았다.
전환 전후의 [tick] 은 이렇다.

| 시점 | sess | frame max | drop | 서버 송신 | 패킷 평균 |
|---|---|---|---|---|---|
| 전환 직전(브로드캐스트) | 792 | 45 ms | 0 | 68.7 MB/s | 9,544 B |
| 전환 후 안정 구간 | 800 | 28~29 ms | 0 | **6.4~7.0 MB/s** | 766~843 B |

**대역이 10배 줄고 프레임 최대치도 낮아졌다.** 전환이 일어난 창 자체는 깨끗했다
(`frame max 45ms`, `drop 0`) — 켤 때 뷰어마다 스냅샷이 한 틱에 몰리는 것을 걱정했는데,
적어도 이 규모에서는 문제가 되지 않았다.

### 그런데 관심영역 경로는 간헐적으로 멈춘다 — 아직 켜면 안 된다

전환 8~13초 뒤부터 창마다 이런 것이 섞인다.

```text
frame avg 874.70 max 1244.84 ms over16 6/6 (1 fps) | sim avg 73.74 ... late 6 drop 6 | 47126 msg/s
frame avg  61.68 max 1100.97 ms over16 27/75 (13 fps) | sim avg 33.47 ... late 9 drop 1 | 37232 msg/s
```

안정 구간(8,7xx msg/s, frame max 29ms)과 폭주 구간(37~47k msg/s, frame 1초)이 번갈아 나온다.
**전환 때문은 아니다** — AoI 를 처음부터 켜 둔 앞의 800명 측정에서도 같은 성격이 보였다
(`late 12` 창). 즉 관심영역 경로 자체가 이 부하에서 스파이키하다.

셀 전이 처리는 이미 증분이다([Map::OnViewerCellChanged](../Engine/Map/Map.cpp) — 새로 들어온
셀과 빠진 셀만 훑는다). 지금 유력한 것은 **부활 파도**다. 이 실행에서 봇이 75초 동안 611번
죽었고, 부활은 텔레포트라서 이전 구독 셀과 새 구독 셀이 전혀 겹치지 않는다 —
그 뷰어의 시야 전체가 leave + enter 로 한꺼번에 나간다. 다만 이건 아직 가설이고,
단계별 계측(구독 갱신 / 메시지 조립 / 송신) 없이는 확정할 수 없다.

**그래서 전 맵의 `aoi_radius` 는 0(끔) 그대로 두었다.** 전환 장치와 계측은 들어갔으니,
이 스파이크의 원인을 잡은 뒤에 맵별 반경을 정하는 것이 순서다.

### 남은 것

- **반경은 맵마다 데이터로 정해야 한다.** 지금은 전 맵이 0(끔)이다. 반경은 성능이 아니라
  "얼마나 멀리까지 보여야 하는가" 라서 맵 설계와 함께 정할 값이고, 위 측정은 그 값이
  정해졌을 때 인구가 얼마부터 이득인지를 말해 줄 뿐이다.
- **교차점은 이 맵/이 분포의 값이다.** 봇은 스폰 15m 안에 뭉쳐 있다. 넓게 흩어진 분포라면
  AoI 가 더 일찍 이긴다(걸러지는 액터가 더 많으므로).
- 17절의 측정 조건 주의(같은 기계에서 IDE·브라우저가 함께 돌았다)가 여기에도 그대로 적용된다.
  같은 실행 안의 비교로만 읽을 것.

## 20. 조치 #11 — 한 월드 1,000명, 틱을 밀지 않게

목표는 하나였다. **월드 하나에 1,000명이 들어와서 틱이 밀리지 않을 것.**
19절이 남긴 상태는 800명에서 관심영역 경로가 간헐적으로 1초씩 멈추는 것이었고,
그대로는 1,000명이 불가능했다.

측정: 맵 1(Starting Village), 1포트/1스레드, 봇 1,000, 램프업 100/s, 120초, `--quest off`.

### 결과부터

| 구성 (1,000명) | sim avg | over100 | late / drop | frame max | 서버 송신 | 패킷 평균 | ping p99 / max |
|---|---|---|---|---|---|---|---|
| 브로드캐스트 | 24.0 ms | **0/50** | 0~3 / **0** | 470 ms | 220~260 MB/s | 21 KB | 145 / 359 ms |
| 관심영역 반경 5 | 33~41 ms | **0/50** | 0~1 / **0** | 270 ms | **46~76 MB/s** | 2~7 KB | **51 / 174 ms** |

접속 1,000/1,000, 로그인 1,000/1,000, 연결 끊김 0. **한 틱 예산 100ms 에 sim 은 33~41ms —
5초 창 50틱 전부가 예산 안이고 drop 은 0이다.** 목표는 관심영역 쪽에서 달성했다.
(브로드캐스트도 이제 틱은 버티지만 240 MB/s 는 내보낼 수 있는 양이 아니다.)

19절 대비 무엇이 달라졌는지가 요점이다 — **800명에서 `frame 874ms / drop 6` 이던 것이
1,000명에서 `frame max 270ms / drop 0` 이 됐다.**

### 원인 1: 보내기가 메시지 하나에 커널 호출 하나였다

19절이 "부활 파도" 를 의심했지만 틀렸다. `[tick]` 을 다시 읽으면 답이 나와 있었다.

```text
frame avg 874.70 max 1244.84 ms | sim avg 73.74 ms | 47126 msg/s
```

**frame 874ms 중 sim 은 74ms 다.** 나머지 800ms 는 월드 로직이 아니라 그 앞의
`worker.PollIo()` — 완료 핸들러 처리다. 그리고 그 완료 핸들러 수는 곧 메시지 수였다.

[GameSession::DoWrite](../Engine/Server.cpp) 는 큐의 **맨 앞 한 통**만 `async_write` 하고,
완료되면 다음 한 통을 다시 걸었다. 메시지 하나에 `WSASend` 하나, 완료 핸들러 하나다.
평소에는 시뮬레이션이 10Hz 라 세션당 한 통이어서 티가 나지 않지만, 전투가 몰려 한 틱에
수십 통이 쌓이는 순간 그 수만큼 커널을 왕복한다.

큐에 쌓인 것을 한 번의 `async_write` 로 모아 보내도록 바꿨다(최대 64통 = 버퍼 128조각).
`send_message` 는 헤더/본문 두 조각을 가리키는 버퍼를 그대로 돌려주므로 이어 붙이기만 하면 된다.

이것 하나로 스파이크가 사라졌다. 지금도 msg/s 는 창마다 11k ↔ 32k 로 오르내리는데
(메시지 **수** 는 줄이지 않았다), frame 은 더 이상 따라 튀지 않는다.

### 원인 2: 스킬 시전 알림이 접속자 수만큼 곱해졌다

[PlayerController::handle(UseSkill)](../Engine/Controller/PlayerController.cpp) 은 시전을
`SendBroadcast` 로 **맵 전원** 에게 보냈다. 관심영역과 무관한 경로라, 시전 한 번이
메시지 N통이 된다 — 사람이 늘면 제곱으로 커지는 유일한 자리였다.

`Map::SendToViewersOf` 를 추가해 **시전자가 있는 셀의 구독자에게만** 보낸다.
관심영역이 꺼진 맵에서는 예전대로 전원에게 간다(작은 맵에서는 그쪽이 싸다).
패킷마다 찍히던 `LOG.info("UseSkill ...")` 도 debug 로 내렸다 — 전투가 몰리면
로그 자체가 틱 스레드의 부하다.

### 원인 3: 셀 이동 처리가 구독자 수의 제곱이었다

`OnActorCellChanged` 는 옛 셀과 새 셀의 구독자 목록을 **서로 선형 탐색** 해 차집합을 구했다.
사람이 몰린 셀에서는 액터 한 마리가 셀을 넘을 때마다 수천 번을 비교하고, 셀을 넘는 액터는
매 틱 수백 마리다. 슬롯 번호로 색인하는 표식 배열(스탬프)로 바꿔 두 목록 길이의 합이 됐다.

### 그리고 부활이 관심영역에서 깨져 있었다

1차 측정에서 봇 1,000마리 중 865마리가 죽은 채로 남았다. 서버 로그를 세어 보니
**서버는 1,698번 부활시켰는데 봇이 인지한 것은 228번** 이었다.

`Map::RespawnPlayer` 는 `TeleportAgent` 후 좌표를 **직접** 써 넣는다
(`SetPosition` + `gridManager_->move`). 그런데 매 틱 도는 `SyncActorState` 는
'네비 위치 != 액터 위치' 로 이동을 감지하므로, 좌표를 미리 맞춰 버린 이 이동은
**'변화 없음' 으로 보인다.** 그래서 셀 전이 처리가 돌지 않고, 부활한 플레이어의 구독 셀은
죽은 자리에 남는다 — 새 자리의 아무것도 못 받고, **자기 자신의 부활조차 못 받는다.**
클라(봇)는 계속 죽은 줄 안다.

좌표를 직접 쓰는 이동을 `Map::MoveActorAndUpdateView` 로 묶어, 관심영역 장부
(구독 셀 이동 + 시야 진입/이탈)까지 함께 갱신하게 했다. 다른 순간이동
(스킬 블링크/넉백, NPC 복귀)은 좌표를 직접 쓰지 않으므로 `SyncActorState` 가 이미 처리한다.

고친 뒤 같은 부하에서 생존 봇이 135명 → 600~870명이 됐다. **위 표는 이 상태의 수치다**
(살아 움직이는 부하라 1차 측정보다 훨씬 무겁다 — 송신량이 3 MB/s 에서 60 MB/s 로 뛴다).

회귀는 [AreaOfInterestTest](../UnitTest/AreaOfInterestTest.cpp) 의
`RespawnMovesInterestToSpawnPoint` 가 고정한다. 고친 코드를 되돌리면 이 테스트가 실패하는 것을
확인했다.

### 맵 1 의 `aoi_radius` 를 5 로 켰다

19절은 스파이크 때문에 전 맵을 0(끔)으로 두었다. 그 스파이크가 위 조치로 사라졌고,
1,000명 구간에서는 관심영역이 대역 4배·p99 3배로 이기므로 맵 1 만 5로 세웠다.
켜고 끄는 것은 여전히 인구가 정한다(700명 이상 켬 / 600명 미만 끔) — 400~600명 구간에서는
브로드캐스트가 더 싸다는 19절의 결론이 그대로다.

나머지 맵은 0 그대로다. 반경은 성능이 아니라 "얼마나 멀리까지 보여야 하는가" 라서
맵 설계와 함께 정할 값이다.

### 남은 것

- **1인당 대역이 아직 크다.** 관심영역에서도 60 MB/s / 1,000명 = 60 KB/s(480 kbps)다.
  봇이 전부 같은 스폰 지점 주변에 뭉쳐서 반경 5 안에 300명 가까이 들어오기 때문이다
  (`view 300`). 스폰 분산이나 시야 안 인원 상한이 다음 지렛대다.
- **메시지 수는 줄이지 않았다.** 창마다 11k ↔ 32k 로 오르내리는 주기(약 20초)의 정체를
  아직 확인하지 않았다. 지금은 모아쓰기가 흡수하고 있어 급하지 않다.
- 측정 조건 주의(같은 기계, 루프백, IDE 동시 실행)는 17·19절과 같다.

## 21. 조치 #12 — 순회 도중 끊기는 세션

20절이 1,000명을 통과시킨 뒤, 다음 목표를 "수치를 더 올리기" 가 아니라 "무너질 곳 막기" 로
잡고 송신 경로를 다시 읽었다. 거기서 부하 측정이 한 번도 건드리지 못한 크래시 경로가 나왔다.

### 무엇이 문제였나

세션당 송신 큐 상한은 이미 있었다(`max_send_queue = 256`, [Server.cpp](../Engine/Server.cpp)).
수신을 멈춘 클라이언트가 서버 메모리를 끌어올리지 못하게 넘치면 그 세션을 끊는다. 문제는
**끊는 자리**다.

```
Map::SendBroadcast      players_ 를 이터레이터로 순회
  Player::Send          →  GameSession::Send
    큐 256 초과         →  Disconnect
      room_.Leave       →  World::BeginDisconnect
        Map::leave      →  players_.erase(지금 순회 중인 바로 그 원소)
```

`unordered_map::erase` 는 그 원소의 이터레이터만 무효화하는데, 하필 그것이 다음에 증가시킬
이터레이터다. 관심영역 경로(`SendToViewersOf`)는 더 나쁘다 — 이쪽은 `SubscribersOf` 가 돌려준
셀 구독자 벡터의 **참조를 들고 순회**하고, `Map::leave` 안의 `UnsubscribeViewer` 가 그 벡터에서
원소를 뺀다. 인구가 임계 아래로 떨어지면 이어지는 `UpdateAoIMode` 가 슬롯 배열 전체를
갈아엎기까지 한다.

중복 로그인 축출([World.cpp](../Engine/World/World.cpp))은 이 위험을 알고 있었다 — 축출 대상을
벡터에 먼저 모으고, `players_.erase` 를 끝낸 뒤에 `Close()` 를 부른다. 송신 큐 상한이 나중에
들어오면서 같은 주의를 받지 못했다.

**부하 측정으로는 영영 볼 수 없는 버그다.** 봇은 받는 즉시 읽어서 큐가 256에 닿지 않는다
(17~20절 전 구간에서 이 사유의 연결 끊김은 0건이었다). 닿는 순간은 서버가 가장 바쁠 때
실제 클라이언트 하나가 버벅이는 순간이다.

### 양쪽에서 막았다

**1) 세션 — 원인.** `GameSession::DisconnectDeferred` 를 만들어 송신 큐 초과 경로가 이것을 쓴다.
입은 즉시 막고(`closed_` — 이후 Send/Read 는 전부 무시된다) 소켓도 그 자리에서 닫지만,
`room_.Leave` 만 `io_context` 로 post 한다. 미뤄진 핸들러는 다음 `PollIo` 에서 실행된다 —
워커 루프가 `PollIo()` 다음에 `UpdateGameLogic()` 을 부르므로, 그 시점에는 어떤 맵도 순회 중이
아니다. 지연은 최대 한 프레임(16ms)이고 그동안 그 플레이어는 아무것도 받지 않는다.

**2) 맵 — 방어선.** `Map::BroadcastScope` 로 순회 깊이를 세고, 깊이가 0이 아닐 때 들어온
`leave` 는 목록에 담아 두었다가 마지막 스코프가 닫히는 자리에서 처리한다. 송신 경로 네 곳
(`SendBroadcast` 둘, `SendToViewersOf`, `SendPendingViews`)에 걸었다. 이제 앞으로 어느 경로에서
순회 중에 끊더라도 컨테이너가 상하지 않는다.

### 검증 — Release 는 이 버그를 못 잡는다

회귀 테스트는 `Player::Send` 를 가로채 "브로드캐스트 순회 도중 퇴장" 을 그대로 만든다
([AreaOfInterestTest](../UnitTest/AreaOfInterestTest.cpp) 의 `BroadcastSurvivesPlayersLeavingDuringSend`,
`ViewerSendSurvivesPlayersLeavingDuringSend`). 셋을 같은 자리에 세우고 **전원이** 첫 Send 에서
떠나게 한다 — 한 명만 떠나면 해시 순서에 따라 그가 마지막 원소일 수 있어 무효한 이터레이터를
증가시키는 경로를 지나가지 않는다.

가드를 빼고 돌려 보면:

| 구성 | 가드 없음 | 가드 있음 |
|---|---|---|
| Release | **통과** (UB 가 우연히 살아남는다) | 통과 |
| Debug | **abort (exit 3)** | 통과 |

Release 에서 멀쩡히 통과하는 것이 이 종류 버그의 성질이다. 잘린 이터레이터를 증가시켜도
해제된 노드의 다음 포인터가 아직 읽히면 그냥 지나간다. **이 회귀 테스트는 Debug 로 돌려야
의미가 있다** — MSVC 체크드 이터레이터(`_ITERATOR_DEBUG_LEVEL=2`)가 그 자리에서 멈춘다.

Release 490개, Debug 490개 전부 통과.

### 남은 것

- **`Player::Send` 를 가상 함수로 바꿨다.** 소켓 없이 이 상황을 재현할 방법이 없어서 만든
  테스트 훅이다. 비용은 무시할 수 있다 — 이 함수는 이미 매 호출 `weak_ptr::lock` 을 지불한다.
- **다른 순회는 아직 훑지 않았다.** 여기서 막은 것은 송신 경로다. 월드 로직 안에서
  플레이어 목록을 도는 다른 자리(진행 로직, 파티, 퀘스트)도 같은 눈으로 볼 필요가 있다.
- **`max_send_queue = 256` 이 맞는 값인지는 재지 않았다.** 20절 관심영역 구성에서 세션당
  틱마다 한 통이므로 여유는 크지만, 상한에 닿는 실제 상황(모바일 회선 끊김 등)을 재현해
  "얼마나 참아 줄 것인가" 를 정한 적은 없다.

## 22. 업데이트 단계를 시스템 매니저로 — 어디까지 되는가

"몬스터 AI 시스템만 왜 `systemManager_` 밖에서 따로 도는가, 이유가 없다면 합치자" 라는
물음에서 시작했다. 이유는 있었지만 좋은 이유는 아니었다 — **`SystemManager` 에 순서 개념이
없어서** 였다.

### 전부는 안 된다

한 틱은 일곱 단계인데, 그중 다섯은 컴포넌트 배열 순회가 아니다.

| 단계 | 하는 일 | ECS 시스템이 될 수 있나 |
|---|---|---|
| 1 UpdateActors | 액터 가상 호출 + 레거시 BT 백엔드 2종 + 스킬 쿨다운 | 스킬 ECS 이관과 레거시 백엔드 제거가 선행 |
| 2 UpdateMovement | `movement_->Update()` — Detour crowd | 불가(외부 라이브러리가 저장소를 소유) |
| 3 UpdateSystems | 컴포넌트 시스템 | 이미 ECS |
| 4 UpdatePlayerDeath | `players_`/`deadPlayers_`/lua 콜백 | 엔티티 단위가 아님 |
| 5 UpdateMonsterSpawns | 스포너 마커 목록 | 엔티티 단위가 아님 |
| 6 UpdateGameMode | lua 구동, 단일 객체 | 불가 |
| 7 SendWorldState | 네트워크 메시지 조립 | 불가 |

제약이 하나 더 있다. **각 단계는 벤치마크와 테스트가 개별로 부르는 공개 API다** —
`BM_BTWorldTickActors` 는 `UpdateActors` 만 불러 18절의 AI 수치를 뽑고, 관심영역 테스트는
`UpdateSystems` 만 불러 상태를 전진시킨다. `Map::update` 를 `systemManager_->Update(dt)` 하나로
접으면 파이프라인을 도는 길이 둘이 되고 조용히 어긋난다.

그리고 lua·Detour·네트워크를 공용 ECS 모듈에 넣으면 `SystemManager` 의 뜻이 "컴포넌트 시스템"
에서 "아무거나 순서대로" 로 희석된다.

### 진짜 문제만 고쳤다

`SystemManager` 에 단계를 넣었다([SystemManager.h](../ECS/SystemManager.h)).

```
PreMovement   이동 목표를 정하는 쪽   (몬스터 AI)
PostMovement  이동 결과를 읽는 쪽     (위치 변경 감지, 타이머)
```

순서는 취향이 아니라 정확성이다. 이동 목표를 정하는 시스템이 이동 뒤에 돌면 모든 결정이
한 틱(10Hz 니까 100ms) 늦게 반영되고, 이동 결과를 읽는 시스템이 이동 앞에 돌면 지난 틱의
위치를 본다. 그 제약이 이제 주석이 아니라 **단계 이름**으로 남는다.

- `AddSystem(unique_ptr<ISystem>, phase)` 를 더해, 원소마다 도는 콜백이 아닌 **배치 패스
  시스템**도 등록할 수 있게 했다. `MonsterAISystem` 이 `engine::ISystem` 을 상속하고
  `PreMovement` 로 등록된다 — 더 이상 특별 취급이 아니다.
- `Map::update` 의 일곱 줄은 그대로다. `UpdateActors` 가 `PreMovement` 를,
  `UpdateSystems` 가 `PostMovement` 를 돌린다. 벤치마크·테스트의 단계별 호출도 그대로다.
- 단계를 나눌 필요가 없는 쪽(ECSTest, ECSBenchmark)은 기존 `Update(float)` 을 그대로 쓴다.
  모든 단계를 순서대로 돈다.

### 덤 — 수명 하나가 정리됐다

예전에는 `aiSystem_` 이 Map 의 `unique_ptr` 멤버라 소멸자 본문이 끝난 뒤에 파괴됐고,
`systemManager_` 는 본문 안에서 `delete` 됐다. 즉 **aiSystem_ 이 자기가 가리키는
EntityManager 보다 오래 살았다.** 소멸자가 그 포인터를 만지지 않아서 드러나지 않았을 뿐이다.
이제 시스템 매니저가 소유하므로 둘이 같이 죽는다 — 액터가 이미 의존하고 있던 그 수명이다.

### 확인

Release 490 / Debug 490 전부 통과, 빌드 경고 0. 백엔드 세 종이 같은 결정을 내리는지는
`MonsterBTTest` 가 그대로 고정한다. 간접 호출이 하나 늘었으므로 AI 단계를 다시 쟀다.

| 몬스터 | 18절 | 이번 |
|---|---|---|
| 1,000 | 0.054 ms | 0.056 ms |
| 10,000 | 0.630 ms | 0.639 ms |

실행 간 흔들림 범위 안이다(18절 측정 주의 참고).

## 23. 조치 #13 — 거리별 갱신 빈도, 그리고 그 전에 나온 버그

19절이 남긴 숙제였다: 관심영역을 켜도 1인당 대역이 60 KB/s(480 kbps)로 크다. 시야 안
액터가 늘면 대역은 `시야 안 액터 수 × 10Hz` 로 곧장 커지는데, 멀리 있는 액터의 좌표를
초당 열 번 보내는 것은 값어치가 없다. 거리에 따라 솎기로 했다.

### 손대기 전에 버그가 하나 나왔다 — 체력과 상태가 전달되지 않았다

`QueueUpdate` 는 액터 포인터만 큐에 담고, 직렬화는 7단계 `SendPendingViews` 가 한다.
그런데 큐에 담는 3단계 `SyncActorState` 는 담자마자 `Actor::ResetChangedFlag()` 를 부른다.
7단계가 읽는 `GetChangedFlag()` 는 이미 0이다.

`Actor::GetActorInfo` 는 위치를 언제나 싣지만 **상태와 체력은 플래그가 서 있을 때만** 싣는다.
그래서 관심영역 모드에서는 시야 안 액터의 위치만 나가고 **체력·상태 변화는 조용히 사라졌다.**
브로드캐스트 경로는 그 자리에서 직렬화하므로 멀쩡했다 — 관심영역을 켠 맵에서만 나타나는
비대칭이었고, 20절에서 맵 1을 반경 5로 켠 순간부터 실재하는 버그였다.

큐에 담을 때 플래그를 함께 복사하도록 고쳤다(`AoIState::PendingUpdate`). 회귀 테스트
`UpdateCarriesStateAndHealthToViewers` 는 세션 없이 검증하려고 `Player::Send` 를 가로채
**실제로 나간 FlatBuffer 를 파싱해서** `state`/`health` 필드가 실렸는지 본다.

### 거리 등급

뷰어 셀에서의 체비쇼프 셀 거리로 나눈다. 셀 한 칸은 2유닛이다.

| 거리 | 주기 | |
|---|---|---|
| 0 ~ 2칸 | 매 틱 | 10 Hz |
| 3 ~ 4칸 | 3틱마다 | 3.3 Hz |
| 그 밖 | 5틱마다 | 2 Hz |

솎는 것은 **위치만 바뀐 경우뿐이다.** 체력·상태·입력잠금이 함께 바뀌었으면 거리와 무관하게
그 틱에 보낸다 — 그것은 사건이라 건너뛰면 영영 사라지지만, 위치는 다음 갱신이 덮어쓴다.
이번 틱이 각 등급의 차례인지는 액터마다 한 번만 계산하고(구독자마다 나눗셈을 하지 않는다),
위상을 액터 번호로 어긋내 먼 액터들이 같은 틱에 몰리지 않게 한다.

### 결과 — 같은 계측을 켠 인접 실행 비교

봇 1,000, 포트 1개, 스레드 1개. 등급 간격만 바꿔(3/5 ↔ 1/1) 두 번 돌렸다.

| | 대조군(1/1) | 등급(3/5) |
|---|---|---|
| 관심영역 메시지 | 10,000 /s | 10,000 /s |
| 메시지당 엔트리 | 85 | **59** |
| 메시지당 바이트 | 2,586 | **1,838** |
| 관심영역 송신 | 25.9 MB/s | **18.4 MB/s** |
| 봇 수신 합계 | 27.3 MB/s | **19.1 MB/s** |

**29% 줄었다.** 틱은 그대로다 — `sim avg 27~28 ms, over100 0/50, late 0, drop 0`.

### 재는 과정에서 배운 것

- **처음 A/B(90초 × 2회)는 아무 차이도 보여주지 못했다**(2,703 MB vs 2,789 MB). 실행 간
  편차가 효과보다 컸다. 같은 계측을 넣고 인접해서 돌린 뒤에야 29%가 보였다. 이 저장소의
  측정 주의(17·18절)가 여기서도 그대로 적용된다 — **집계된 총량이 아니라 기전을
  세어야 한다**(메시지당 엔트리 수).
- **송신의 약 75%가 관심영역 갱신 메시지다**(초당 10,000건, 20.6 MB/s). 나머지는 미미하다.
  엔트리 하나는 31바이트로 정상이다 — 프레이밍 낭비는 없다.
- **`aoi_radius` 는 셀이 아니라 유닛이다.** 맵 1의 5는 2.5셀이라 실제 최대 거리가 3이고,
  지금 구성에서 '먼' 등급(4칸 초과)은 한 번도 걸리지 않는다. 사실상 2단 구성으로 돌고 있다.
  거리 분포는 d0 3%, d1 17%, d2 33%, d3 47% 였다.

### 남은 것

- **위치 잔차.** 멀리 있는 액터가 '솎이는 틱' 에 멈추면 마지막 이동분이 전달되지 않는다
  (최대 속도 4.5 u/s × 0.4s ≈ 1.8유닛). 다음에 움직이면 스스로 낫고, 실제로는 멈출 때
  상태도 함께 바뀌는 경우가 많아 사건 경로로 그 틱에 나간다. 상한을 두려면 '방금 멈췄다'
  를 사건으로 만들어야 하는데, 그 비트를 `StateComponent` 에 넣으면 12→16바이트가 되어
  가장 뜨거운 배열이 33% 커진다. 지금은 두었다.
- **경계값은 아직 튜닝하지 않았다.** 최대 거리가 3이므로 `kAoINearCells` 를 1로 좁히면
  d2(33%)까지 솎여 더 줄지만, 4~6유닛 거리의 움직임이 눈에 띄게 끊긴다. 눈으로 확인한
  뒤에 정할 값이다.
- **1인당 대역은 19 KB/s 수준이 됐다**(19.1 MB/s / 1,000명). 480 kbps 에서 150 kbps 다.

## 24. async_write 하나가 25us — 그리고 그 값이 바이트와 무관하다는 것

23절 뒤에 남은 질문은 하나였다. 10Hz 틱의 `sim` 을 무엇이 먹고 있는가.
직전 계측이 이렇게 답했다.

```
sim 합계            240 ms/s   (24 ms x 10틱)
SendPendingViews    237 ms/s
  |- serialize       43 ms/s   18%
  \- send           185 ms/s   77%   <- 전부가 boost::asio::async_write
```

`async_write` 호출 하나가 17us 였다. 그런데 이 측정은 **서버와 봇 1,000명이 같은
기계에서 소켓 2,000개를 물고 도는 환경**이다. 루프백 `WSASend` 는 수신측 전달을
그 자리에서 해 버리므로, 17us 가 진짜 비용인지 측정 환경의 경합인지 알 수 없었다.
이 값에 따라 다음 수가 갈린다.

- 진짜 비용이면 → 줄일 방법은 **호출 수를 줄이는 것뿐**이고, 호출 수 = 세션 x 송신
  주기이므로 곧 동기화 품질을 깎는 일이 된다.
- 경합이면 → send 가 60 ms/s 로 내려앉아 serialize(43 ms/s)와 같은 급이 되고,
  품질을 건드릴 이유 없이 직렬화/조각 공유 쪽이 정답이 된다.

### 재는 법 — 인원을 바꿔 가며 호출 하나의 비용을 본다

경합이면 인원에 따라 커지고, 고정 비용이면 평평하다. 서버
`x64\Release\Game.exe 65001 --config ...`(포트 1개 = 월드 1개 = 스레드 1개), 봇
`Bot.exe --port 65001 --bots N --threads 8 --duration 90 --rampup 50 --quest off`,
구성마다 서버를 새로 띄웠다. `[tick]` 줄에 `write N/s, us, batch` 를 임시로 붙였다.

**시계 자체의 비용부터 뺐다.** `steady_clock::now()` 를 빈 구간으로 한 쌍 더 불러
같은 실행에서 함께 쟀더니 **0.02us** 였다(TSC 기반). 호출당 계측 부담은 0.04us,
초당 0.4ms 로 무시할 수 있다. 즉 아래 값은 보정 없이 그대로 읽어도 된다.

| 세션 | 모드 | 메시지 크기 | write/s | **us/write** | write 합계 | sim 합계 |
|---|---|---|---|---|---|---|
| 300 | 브로드캐스트 | 5.7 KB | 3,900 | **19.0** | 74 ms/s | 65 ms/s |
| 600 | 브로드캐스트 | 13.5 KB | 7,200 | **25.7** | 185 ms/s | 172 ms/s |
| 1,000 | 관심영역 | 1.7 KB | 11,000 | **25.5** | 281 ms/s | 345 ms/s |

(300/600 에서 write 합계가 sim 합계보다 큰 것은 모순이 아니다. `OnWrite` 가 다시 거는
write 는 완료 핸들러 쪽, 즉 `PollIo` 에서 실행되므로 `frame` 에는 들어가고 `sim` 에는
들어가지 않는다.)

### 답 — 경합이 아니다. 그리고 바이트와 무관하다

**인원을 1,000에서 300으로 줄여도 26% 밖에 싸지지 않는다.** 600과 1,000은 사실상
같다. 경합이라면 인원에 비례해 내려가야 했다. 17~25us 는 진짜 비용이다.

더 결정적인 것은 같은 표의 3열과 5열이다.

- 600명, 브로드캐스트, 메시지 **13.5 KB** → **26.07 us**
- 1,000명, 관심영역, 메시지 **1.7 KB** → **25.48 us**

**페이로드가 8배인데 비용이 같다.** 배치 크기로 갈라 봐도 마찬가지다 — 같은 창 안에서
`batch 1.00` 과 `batch 1.54` 의 us/write 가 구분되지 않는다.

```
600명  batch 1.00 -> 26.07 / 25.98 / 22.34 / 27.48 us
       batch 1.4~1.5 -> 24.55 / 27.14 / 26.90 / 25.78 us
```

즉 이 비용은 **호출 하나당 고정**이다. 실린 바이트에도, 실린 메시지 수에도 붙지 않는다.

### 이것이 바꾸는 것

지금까지 "송신이 비싸다" 를 한 덩어리로 다뤘는데, 실은 **서로 다른 두 문제**였고
대책도 반대편에 있었다.

| | 무엇이 줄이나 | 지금 크기 |
|---|---|---|
| **서버 CPU** | `async_write` **호출 수** | sim 의 81% (281/345 ms/s) |
| **클라이언트 대역** | 메시지 **바이트** | 1인당 19 KB/s |

23절의 거리별 등급, 그리고 논의하던 그리드 조각 공유/구조체 포맷은 전부 **바이트**
쪽이다. 그것들은 sim 의 81%를 건드리지 못한다 — 8배 큰 메시지가 같은 값을 찍었으므로.
반대로 CPU 를 줄이려면 호출 수를 줄여야 하는데,

```
writes/s = 세션 수 x 송신 주기
```

이고 10Hz 에서 세션당 메시지가 정확히 하나라 **묶을 것이 없다**. 남는 수는 주기를
낮추는 것뿐이고, 그것이 곧 동기화 품질이다. 공짜 점심이 없다는 뜻이다.

### 그래서 지금은 깎지 않는다

품질을 내줄 이유가 없다. 1,000명에서 목표는 이미 서 있다.

```
sess=1000 | sim avg 34.6 max 41 ms over100 0/50 late 0 drop 0 | out 17 MB/s
```

`over100 0`, `drop 0`, 끊긴 세션 0, 워커 스레드 점유율은 절반 이하(frame avg 15ms /
32fps = 47%)다. 대가를 치러야 하는 최적화는 대가를 치를 이유가 생겼을 때 한다.

~~남은 판단은 25us 라는 값 자체다. 실제 NIC 로 나가는 `WSASend` 는 보통 2~5us 인데,
루프백은 수신측 소켓 버퍼 전달을 그 자리에서 끝낸다. 이 값이 배포 환경에서도 25us 인지는
기계 두 대로 나눠 재기 전에는 알 수 없다.~~

**28절에서 열어 봤다. 이 기대는 과했다.** asio 를 빼고 커널만 재니 TCP 루프백 10.7us,
UDP 루프백 8.4us 였다 — 차이가 2.3us 뿐이다. 즉 **루프백 때문이 아니라 소켓 전송
자체(시스템콜 + Winsock + 필터 계층)가 8us 대**이고, 그 몫은 실제 NIC 로 보내도 낸다.

### 부산물 — `write/s` 와 `batch` 는 상시 계측으로 남겼다

`[tick]` 줄에 `write N/s batch M` 이 붙는다. 시계 호출 없이 증가 연산 둘이라 공짜이고,
sim 의 81%를 결정하는 값이 호출 수인 이상 "얼마나 보냈는가(msg/s, MB/s)" 만으로는
부족하다. 타이밍(us/write)은 시계 호출이 들어가므로 남기지 않았다.

### 23절에서 미뤄 둔 항목에 대한 결론

- **`kAoINearCells` 2 -> 1 은 하지 않는다.** 바이트를 더 줄이지만 sim 의 81%는 그대로고,
  4~6유닛 거리의 움직임이 눈에 띄게 끊긴다. 서버 CPU 를 사지 못하는 화폐로 품질을
  치르는 거래다.
- **위치 잔차**(먼 액터가 솎이는 틱에 멈추면 마지막 이동분이 안 나가는 것)는 그대로
  남는다. `StateComponent` 를 12 -> 16바이트로 키우는 값이라, 실제로 보이는지 확인한
  뒤에 정한다.

## 25. 조치 #14 — 맵마다 다른 관심영역 반경, 그리고 시야가 짧았다는 것

20절에서 맵 1에 `aoi_radius: 5` 를 넣었다. 1,000명을 예산 안에 넣으려고 고른 값이고,
나머지 맵 다섯은 0(브로드캐스트)으로 남아 있었다. 그 다섯에 값을 넣는 것이 이번 일이다.

### 먼저 이 숫자가 무슨 뜻인지부터 확정했다

`aoi_radius` 는 **셀이 아니라 월드 단위**다. 구독은 이렇게 정해진다.

```
R = ceil(aoi_radius / kGridCellSize)      // kGridCellSize = 2
뷰어는 자기 셀에서 R 칸까지, (2R+1)^2 개 셀을 구독한다
```

뷰어가 셀 안 어디에 서 있느냐에 따라 실제 시야가 달라진다. 오른쪽 끝에 서 있으면 왼쪽은
2R+2 유닛까지 보이지만 오른쪽은 2R 유닛에서 끊긴다. 즉 **보장되는 시야는 2R 유닛**이고,
셀 크기가 2 이므로 결국 **적은 숫자가 곧 보장 시야(유닛)** 다.

### 그러자 기존 값이 게임 스케일보다 짧다는 것이 드러났다

맵 1 의 5 는 `R = ceil(2.5) = 3`, 보장 시야 **6유닛**이다. 게임 값과 나란히 놓으면
이렇게 된다.

| | 거리 |
|---|---|
| 관심영역 보장 시야 (`aoi_radius: 5`) | **6 유닛** |
| 몬스터 적 탐지 `g_fDistance` | **10 유닛** |
| 스킬 최대 사거리 | **14 유닛** (12~14 짜리가 54종 중 5종) |
| 클라 카메라(거리 15 / 높이 6 / 45도)가 담는 지면 | 대략 **20 유닛** |

**몬스터가 10유닛에서 나를 인지하고 달려오는 동안, 나는 그 몬스터를 6유닛까지 못 본다.**
화면 한복판에 튀어나온다. 부하 시험에서는 안 보였다 — 봇은 받은 것만 공격하므로
스킬 거부가 2건밖에 안 났고, 서버 로그에도 아무 흔적이 없다. 사람 눈으로만 보이는 종류다.

이 결함은 20절이 만든 것이 아니라 20절이 **드러낸** 것에 가깝다. 그 전까지 이 맵들은
전부 브로드캐스트라 시야라는 개념 자체가 없었다.

### 그래서 하한을 정하고, 상한은 재서 정했다

하한은 게임이 정한다(최소 10, 되도록 14~20). 상한은 비용이 정한다 — 창이 `(2R+1)^2`
로 커지므로 좁은 맵에서는 금세 맵 전체가 된다. 맵 1(51x50 유닛 = 29x28 = 812셀)에
1,000명을 넣고 반경만 바꿔 쟀다. 각 구성마다 서버를 새로 띄웠다.

| `aoi_radius` | R | 창(셀) | 맵 대비 | 보장 시야 | sim avg / max | over100 | late | 서버→클라 | 봇 수신(90초) | ping p99 / max |
|---|---|---|---|---|---|---|---|---|---|---|
| 5 (기존) | 3 | 49 | 6.0% | 6 u | 32~35 / 41 ms | 0/50 | 0 | 13~15 MB/s | 1,617 MB | 53 / 131 ms |
| **10** | 5 | 121 | 14.9% | 10 u | **38~41 / 58 ms** | **0/50** | 0~1 | 24~31 MB/s | 2,688 MB | 68 / 221 ms |
| 14 | 7 | 225 | 27.7% | 14 u | 44~51 / **96** ms | 0/50 | 0~3 | 32~49 MB/s | 3,699 MB | 124 / 274 ms |
| 20 | 10 | 441 | 54.3% | 20 u | 43~60 ms | **3/41** | 0~6 | 34~68 MB/s | 4,369 MB | 131 / 289 ms |

14 는 `over100` 이 0 이지만 sim max 가 96ms 로 예산에 붙어 있다. 20 은 넘긴다.
**10 이 게임 하한을 만족하면서 여유가 남는 유일한 값**이라 이것을 골랐다.

> **이 표의 절대값에는 전제가 있다**(26절에서 알게 됐다). 네 구성 모두 같은 봇 계정을
> 재사용해서 돌렸는데, 봇 계정은 마지막 위치가 DB 에 남는다(`DAOPlayerLocation`).
> 즉 봇들이 맵 곳곳에 흩어진 상태로 시작했다. 새 계정(`--prefix`)으로 돌리면 전원이
> `player_spawn` 한 점에 뭉쳐서 시작하는데, 같은 반경 10 이 그때는 이렇게 나온다.
>
> | 맵 1, 1,000명, 반경 10 | sim avg / max | over100 | 서버→클라 |
> |---|---|---|---|
> | 흩어진 시작(계정 재사용) | 36~40 / 53 ms | 0/50 | 21~28 MB/s |
> | 뭉친 시작(새 계정) | **52~61 / 208 ms** | 0~2 / 45 | **56~75 MB/s** |
>
> 끊김 0, `drop` 0 으로 견디기는 하지만 여유는 절반이다. **네 구성의 순서는 그대로이므로
> 반경 10 이라는 선택은 바뀌지 않는다** — 다만 "여유가 남는다" 는 흩어진 경우의 이야기다.

### 맵 크기가 이 계산을 완전히 바꾼다

navmesh 경계에서 읽은 실제 크기다(`size` 필드는 믿을 수 없다 — Dragon's Lair 는
502x502 로 적혀 있는데 마커는 103유닛만 차지한다. 서버는 이 필드를 파싱만 하고 쓰지 않는다).

| 맵 | navmesh 범위 | 그리드 | 실제 크기 | 면적 | 반경 20 이면 창이 |

## 26. 맵 15 를 실제로 재 봤다 — 25절의 추정이 틀렸다

25절에서 맵 15(Arcadia Plains, 502x502)에 반경 20 을 주고 "창이 맵의 0.68% 라 안전할
것" 이라고 적었다. 재지 않은 채로. 재 보니 **실패한다.**

### 봇을 맵 15 에 넣는 것부터가 일이었다

맵 15 는 들어오는 게이트가 없다(서버가 기동할 때 `데이터 정합성: map 15 로 들어오는
게이트가 없습니다` 경고를 이미 남기고 있었다). 봇은 로그인하면 `GetPrimaryMap()`
= `mapList_.front()` 로 가는데, 그 목록은 **field 맵 id 오름차순**이라 항상 맵 1 이다.

그래서 정렬 비교자를 임시로 바꿔 맵 15 를 front 로 올렸다(다른 맵 4개는 그대로
로드되므로 월드 구성은 이전 측정과 같다). 그런데 첫 시도에서 봇이 그대로 맵 1 로 갔다 —
**봇 계정의 마지막 위치가 DB 에 남아 있었다.** `SendLoginSuccess` 는 저장된 맵이 로드되어
있으면 그쪽을 우선한다(`DAOPlayerLocation`). `--prefix` 로 새 계정을 쓰니 맵 15 로 갔다.

### 결과 — 반경 20, 1,000명

```
frame avg 70~420 ms  max 2,223 ms   (2~11 fps)
sim   avg 20~85 ms   max 218 ms     over100 최대 5/22, drop 3~5
out   30~48 MB/s     msg/s 94,000~176,000   avg 200~420 B
write 7,400~21,000/s batch 8~18
세션  1000 -> 642 -> 922 -> 1000 (오르내린다)
```

**전송 큐 넘침으로 1,909 세션이 끊겼다.** 21절에서 넣은 `DisconnectDeferred` 가 처음으로
실제 부하에서 발동했다 — 그것이 없었다면 순회 중 컨테이너가 무효화되어 크래시였다.
안전망이 제 몫을 했다는 뜻이지, 이 구성이 돌아간다는 뜻은 아니다.

800명으로 낮춰도 마찬가지다(끊김 2,784건, frame max 2,124ms).

### 눈에 띄는 것 — sim 은 멀쩡한데 frame 이 터진다

`sim avg 13~31ms` 인데 `frame max 2,124ms` 다. 월드 틱은 예산의 3분의 1도 안 쓴다.
무너지는 곳은 **완료 핸들러 처리(PollIo)** 다. 24절에서 "비용은 호출 하나당 고정" 이라고
했던 것의 수신측 대칭이다 — 메시지가 작아도(200~420 B) 개수가 많으면 그대로 프레임을
먹는다.

### 그래서 개수의 출처를 셌다

`GameSession::Send` 에서 메시지 종류별로 세어 `[tick]` 에 찍었다.

```
t9 = 63,000~182,000/s      <- UseSkill
t5 =   9,400/s             <- UpdateActorNotify (세션당 틱 1통. 정상)
t6 =     900/s             <- Ping
```

**t5 는 정상이다.** 1,000세션 x 10Hz = 10,000/s 이고 실제로 9,400/s 다. 관심영역은
설계대로 동작하고 있다.

문제는 t9 다. 봇이 90초에 스킬을 15,889회 썼으니 **초당 177회**인데, 나가는 알림은
**초당 18만 건**이다. 시전 하나가 1,000명에게 간다.

### 그런데 코드는 이미 옳다

`PlayerController::handle(const UseSkill*)` 은 `SendToViewersOf` 를 쓴다. 주석까지
달려 있다 — "맵 전원에게 보내면 시전 한 번이 접속자 수만큼의 메시지가 된다".

문제는 **군중이 관심영역을 무력화한다**는 것이다. 봇 1,000명이 맵 15 의 유일한
`player_spawn`(-146.2, -47.3) 한 점에 스폰되어 거기 뭉쳐 있다. 반경 20 이면 창이
42x42 유닛이라 **그 안에 1,000명이 다 들어간다.** 502x502 맵이라는 사실이 아무 의미가
없다. 시야를 좁히면 팬아웃이 줄어든다는 것도 그대로 확인된다.

| 맵 15, 1,000명 | 끊김 | sim avg / max | over100 | msg/s |
|---|---|---|---|---|
| 반경 20 | **1,909** | 20~85 / 218 ms | 최대 5/22 | 94,000~176,000 |

반경 10 이어도 예산은 넘는다. **반경은 원인이 아니라 증폭기다.**

### 정정과 결정

- **맵 15 를 반경 10 으로 내렸다.** 20 을 검증할 방법이 지금 없다. 봇이 한 점에
  스폰되는 한 맵 크기가 계산에 들어오지 않아서, 이 하네스로는 "넓은 맵이라 싸다" 를
  보일 수가 없다. 검증되지 않은 값보다 검증된 값을 둔다 — 10 은 몬스터 탐지 반경을
  만족하는 하한이기도 하다.
- **25절의 추정을 취소선으로 남겼다.** 지우지 않은 이유는, 틀린 방식이 반복될 만한
  것이기 때문이다. 액터가 고르게 퍼져 있다고 가정했고 비용을 바이트로 셌다. 24절이
  같은 문서에서 "비용은 바이트가 아니라 호출 수" 라고 결론 낸 바로 다음 절이었다.

### 남는 것 (열린 항목)

- **군중에서는 관심영역이 이벤트 팬아웃을 못 막는다.** 시전 하나가 같은 셀을 보는
  전원에게 가고, 광장/월드보스/공성처럼 사람이 뭉치는 순간이 정확히 그 상황이다.
  상한(예: 셀당 이벤트 수신자 N명으로 자르기, 거리별 이벤트 솎기)이 필요하지만
  설계 변경이라 여기서는 하지 않았다.
- **맵 15 는 여전히 도달 불가다**(`gates: 0`). 부하로 재려면 primary 맵 정렬을 임시로
  바꾸고 `--prefix` 로 새 계정을 써야 한다. 게이트를 놓기 전까지 이 맵의 수치는 전부
  이 우회로 얻은 것이다.
- **`player_spawn` 이 한 점이라 스폰이 뭉친다.** 넓은 맵일수록 이것이 측정을 왜곡한다.
  맵 15 에 스폰 마커를 여러 개 두면 하네스가 맵 크기를 실제로 반영하게 된다.
- **부하 시험 결과는 봇 계정을 재사용했는지에 따라 달라진다.** 맵 1 반경 10 이
  흩어진 시작에서는 sim 36~40ms, 뭉친 시작에서는 52~61ms 다(같은 인원, 같은 설정).
  앞으로 수치를 비교할 때는 `--prefix` 를 함께 적어야 한다. 25절 표에 단서를 달았다.
- **봇 계정의 마지막 위치가 DB 에 남는다.** 스폰 맵을 바꾸는 실험은 `--prefix` 를 함께
  바꾸지 않으면 조용히 이전 맵으로 간다(첫 시도에서 그렇게 됐다).

## 27. 병목은 어디인가 — 프레임을 끝까지 쪼개 봤다

24~26절이 "송신이 비싸다" 를 여러 각도에서 보여 줬는데, 정작 **프레임 전체를 한 장으로
쪼갠 적이 없었다.** 워커 루프(`PollIo` -> `UpdateGameLogic`)와 `Map::update` 의 7단계를
한 번에 계측했다. 맵 1, 반경 10, 새 계정(뭉친 시작), 1,000명.

계측은 `thread_local` 누적 + 시간 창(5초)이다. 월드가 워커 스레드에 고정돼 있어 맵
5개가 자연히 합산된다. 창을 개수가 아니라 시간으로 끊은 것은 23절에서 한 번 틀렸기
때문이다(맵마다 카운터를 세면 창 길이가 맵 수만큼 짧아진다).

### 먼저 — 이 측정은 반복하면 25% 흔들린다

같은 빌드, 같은 부하로 네 번 돌린 결과다.

| 실행 | sim ms/s | frame ms/s | SEND | sys | write/s | entries/s |
|---|---|---|---|---|---|---|
| A | 561 | 678 | 497 | 42 | 11,545 | 2,437,579 |
| B | 406 | 507 | 355 | 38 | 11,519 | 2,346,772 |
| C | 416 | 515 | 367 | 39 | 11,558 | 2,377,018 |
| D | 517 | 621 | 452 | 41 | 11,459 | 2,394,305 |

**부하는 같다** — `write/s` 는 ±0.4%, `entries/s` 는 ±2% 안에 있다. 그런데 시간은
±25% 흔들리고, **흔들리는 것은 전부 `SEND` 다.** 순수 CPU 작업인 `sys` 는 38~42 로
안정적이다.

즉 편차의 출처는 기계 전반이 아니라 **루프백 `async_write` 하나의 비용**이다.
`SEND` 에서 안정적인 직렬화 몫(약 199 ms/s)을 빼고 역산하면 호출당 **13.6us ~ 24.8us**
사이를 오간다. 24절에서 "이 값이 배포 환경에서도 25us 인지는 기계 두 대로 나눠 재기
전에는 알 수 없다" 고 적어 둔 것이 여기서 다시 나온다.

**그래서 아래 절대값은 폭으로 읽어야 하고, 결론은 실행 안에서 동시에 잰 비율과
안정적인 카운터(`write/s`, `entries/s`)에만 기댄다.**

### 1,000명 프레임의 내역

가장 느렸던 실행 A(내부 타이머까지 넣어 `SEND` 를 쪼갠 회차)다.

```
[phase] 합계 538 ms/s | actors 4 move 1 sys 43 death 1 spawn 0 mode 0 SEND 489
                        acq 1  ser 199  wr 285 | viewers 9,975/s entries 2,340,900/s (234.7/msg)
[tick]  frame avg 22.67 (27 fps) | sim avg 53.84 | over100 0/50 late 0 drop 0 | write 10,905/s
```

`[phase]` 합계 538 과 `sim avg 53.84 x 10 = 538` 이 정확히 맞는다. `frame avg x fps` 에서
`sim` 을 빼면 `PollIo` 가 나온다.

| 구간 | ms/s | 프레임 대비 | 성격 |
|---|---|---|---|
| **async_write** | 285 (155~285) | **43%** | 환경에 따라 흔들림 |
| **직렬화(FlatBuffers)** | 199 | **31%** | 안정 (83 ns/entry) |
| **완료 핸들러(PollIo)** | 112 | 17% | |
| `UpdateSystems`(ECS + 관심영역 `QueueUpdate`) | 42 | 6% | 안정 |
| 나머지 월드 로직(actors/move/death/spawn/mode) | 11 | **2%** | 안정 |
| 버퍼 대여 | 1 | 0% | |
| **프레임 합계** | 667 (507~678) | | 워커의 **51~68%** |

**송신 경로가 프레임의 91% 다. 월드 시뮬레이션 자체는 2% 다.**
18절에서 AI 를 ECS 로 바꾼 뒤로 월드 틱이 병목 근처에도 없다는 것이 다시 확인된다.

### 더 중요한 것은 각 항이 어떻게 자라느냐다

여기서는 흔들리는 시간을 쓰지 않는다. **안정적인 두 카운터만으로 결론이 난다.**
관심영역은 700명에서 켜지므로 임계 위의 두 점을 비교했다(500명은 브로드캐스트라
같은 경로가 아니다 — `viewers 0/s` 로 확인).

| | 800명 | 1,000명 | 배율 | 지수 |
|---|---|---|---|---|
| **write/s** (= async_write 호출 수) | 9,060 | 11,500 | 1.27x | **N^1.1 — 선형** |
| entries/메시지 | 176 | 242 | 1.37x | |
| **entries/s** (= 직렬화할 필드 수) | 1.41M | 2.39M | **1.70x** | **N^2.4 — 제곱** |
| (참고) ns/entry | 88.6 | 83.0 | — | 상수 |
| (참고) us/write | 24.9 | 24.8 | — | 상수 |

단가(ns/entry, us/write)가 두 인원에서 같으므로, **시간은 개수를 그대로 따라간다.**

- **선형 항 = `async_write`.** 세션 하나가 틱마다 한 통 받는다. 24절대로 호출당 고정
  비용이고 바이트와 무관하다. **줄이려면 송신 주기를 낮추는 수밖에 없고, 그것이 곧
  동기화 품질이다.**
- **제곱 항 = 직렬화 + `UpdateSystems`.** 뷰어마다 창 안 액터를 처음부터 다시 쓴다.
  `QueueUpdate` 가 액터 변경 하나를 그 셀 구독자 전원의 대기열에 밀어 넣는 것도 같은
  항이다. **인원 x 창 안 인원** 이라 밀집도에 제곱으로 붙는다.

### 교차점은 async_write 가 실제로 얼마냐에 달렸다

```
직렬화 198 ms/s x (N/1000)^2.4   vs   write 11,500/s x us_write x (N/1000)
```

| async_write 단가 | 두 항이 같아지는 인원 |
|---|---|
| 25us (루프백 느린 회차) | 약 **1,300명** |
| 13.6us (루프배 빠른 회차) | 약 **850명** — 이미 넘었다 |
| ~11us (실제 NIC — 28절에서 잰 소켓 바닥값 8.4us + a) | 약 **1,050명** |

**실제 배포에서 write 가 싸질수록 직렬화가 더 빨리 지배한다.** 즉 이 항은 지금 크기가
아니라 자라는 방향 때문에 중요하다. (write 가 얼마나 싸질 수 있는지는 28절에서 쟀다 —
소켓 전송 바닥값이 8.4us 라 생각만큼 내려가지 않는다.)

### 한 워커의 한계선

프레임이 1,000 ms/s 에 닿으면 포화한다. 위 지수로 늘리면 느린 회차 기준

```
1,000명  667 ms/s (실측)
1,200명  ~840 ms/s
1,400명  ~1,040 ms/s  <- 포화
```

**한 월드 = 한 스레드의 한계는 대략 1,300~1,400명이다.** 뭉친 시작 기준이고, 흩어져
있으면(25절) 제곱 항이 작아져 더 올라간다.

### 그래서 1,000명은 어려운가 — 아니다

맵 1 기준으로 입장도 유지도 된다.

```
로그인 1000/0, 스폰 1000/0, 연결 끊김 0, 레이트리밋 보류 0
over100 0/50, late 0, drop 0, 워커 점유율 51~68%
Ping p50 21 / p95 62 / p99 155 ms
```

26절에서 무너진 것은 인원이 아니라 **맵 15 의 이벤트 팬아웃**(UseSkill 초당 18만 건)
이었다. 그것은 이 표의 어느 항도 아니고 관심영역 밖에서 벌어지는 별개의 문제다.

### 다음 수가 어디인지도 이 표가 말해 준다

제곱 항은 **그리드 조각 공유**로 선형이 된다. 셀마다 한 번 직렬화해서 그 셀을 보는
전원이 같은 버퍼를 나눠 쓰면 `entries/s` 가 `인원 x 창 안 액터` 에서 `전체 액터 수` 로
떨어진다 — 1,000명에서 2.39M/s -> 약 12,000/s.

24절에서는 이 방향을 "비용의 18% 를 겨냥한다" 고 평가했다. **그 평가는 반경 5,
흩어진 시작에서 잰 값이었다.** 반경을 게임 하한(10)으로 올리고 사람이 뭉치자 같은
항이 31% 가 됐고, 무엇보다 **자라는 쪽이 이쪽이다.** 선형 항은 품질을 깎지 않고는
못 줄이지만, 제곱 항은 품질 손실 없이 줄일 수 있다.

### 계측은 남겼다(단계 7개 + 개수 2개)

`[phase]` 줄은 상시로 둔다 — 설정이 바뀔 때마다 비율이 크게 달라지는 것을 25~27절에서
세 번 겪었다. 비용은 틱당 시계 7쌍(초당 수십 마이크로초)이다. **뷰어 루프 안에는 시계를
두지 않았다** — 거기는 초당 만 번이다. 대신 `viewers` 와 `entries` 는 증가 연산뿐이라
공짜인데, 이번 절에서 **가장 믿을 만한 신호가 바로 이 둘이었다.** 시간은 흔들려도
개수는 안 흔들린다.

`SEND` 안의 직렬화/전송 비율이 필요하면 `[tick]` 의 `write/s` 로 유도한다:
`write ms/s = writes/s x us_write`, `직렬화 = SEND - write`. 단, `us_write` 를 상수로
두면 안 된다 — 이 절이 보여 준 대로 회차마다 13~25us 를 오간다.

## 28. async_write 가 왜 43% 인가 — 25us 를 열어 봤다

27절에서 `async_write` 가 프레임의 43% 라는 것까지 나왔는데, **왜 호출 하나가 그렇게
비싼지는 열어 보지 않았다.** 24절에서도 "진짜 비용이다" 까지만 확인하고 멈췄다.

단서는 하나 있었다. 같은 부하에서 회차마다 13.6us <-> 24.8us 로 흔들린다는 것.
순수 유저공간 코드(asio 오버헤드, 핸들러 할당, atomic)라면 2배씩 흔들릴 리가 없다.
그래서 **asio 를 통째로 빼고 커널만** 재는 마이크로벤치를 만들었다.

### 재는 법

asio 의 `async_write` 가 결국 하는 일과 같은 모양으로 맞췄다 — IOCP 에 붙인 소켓 +
`OVERLAPPED` + `WSABUF` 2개(헤더 + 본문). asio / 핸들러 / `shared_ptr` 은 전부 뺐으므로
여기서 나온 값이 곧 **커널 몫**이다. 피어는 별도 스레드 4개가 계속 읽어 비운다.
앞 20라운드는 워밍업으로 버리고 40라운드를 쓴다.

### 결과

| 조건 | us / 호출 |
|---|---|
| TCP 루프백, 100 소켓, 2000B | **10.10** |
| TCP 루프백, 300 소켓, 2000B | **10.24** |
| TCP 루프백, 1,000 소켓, 2000B | **12.02 / 13.79** |
| TCP 루프백, 1,000 소켓, 200B | 14.66 |
| TCP 루프백, 1,000 소켓, 1300B | 10.66 |
| **UDP 루프백, 1,000 소켓, 1300B** | **8.40** |
| (참고) 서버 실측 `async_write` 전체 | 13.6 ~ 24.8 |

### 세 가지가 확인된다

**1. 소켓 수는 거의 무관하다.** 100개 10.10us, 1,000개 12.02us — 10배인데 19% 다.
24절에서 봇 수를 300/600/1,000 으로 바꿔 봤을 때와 같은 결론이 커널 수준에서 다시
나왔다. **경합이 아니다.**

**2. 바이트도 거의 무관하다.** 200B 와 2000B 가 구분되지 않는다. 서버에서 13.5KB 와
1.7KB 가 같은 값을 찍었던 것(24절)의 커널 쪽 근거다. **호출당 고정 비용이다.**

**3. 루프백 때문이 아니다 — 이것이 새로운 것이다.**
TCP 10.66us, UDP 8.40us. 차이는 **2.3us** 뿐이다. UDP 는 TCP 상태머신과 스트림 전달
경로를 건너뛰지만 소켓 계층과 WFP(Windows 필터링 플랫폼, 방화벽/Defender 콜아웃)는
그대로 지난다. 즉

```
8.4us   소켓 전송 자체(시스템콜 + Winsock + 필터 계층)   <- 배포에서도 그대로 낸다
2.3us   TCP 스택 + 루프백 전달                           <- 실제 NIC 면 달라지는 부분
```

**24절과 27절에서 "실제 NIC 면 2~5us 라 훨씬 싸질 것" 이라고 적었는데, 그 기대는
과했다.** 줄어드는 것은 위 2.3us 쪽이고, 8.4us 는 어디로 보내든 낸다.

### 그래서 43% 의 내역

1,000명 기준으로 이렇게 쌓인다.

| | us/호출 | ms/s | 성격 |
|---|---|---|---|
| 소켓 전송 바닥값 (시스템콜 + Winsock + 필터) | ~8.4 | ~97 | **줄일 수 없다** |
| TCP 스택 + 루프백 전달 | ~2.3 | ~26 | NIC 면 달라짐 |
| asio 계층(합성 연산, `shared_from_this`, 핸들러 할당) | 0~3 | 0~35 | 작다 |
| 기계 상태 / 봇 프로세스와의 경합 | 0~11 | 0~127 | 측정 환경 |
| **합계** | **13.6~24.8** | **155~285** | |

그리고 앞에 곱해지는 것이 **호출 수**다.

```
writes/s = 세션 수 x 틱 주기 = 1,000 x 11 = 11,500/s
```

세션 하나가 틱마다 정확히 한 통을 받으므로 `batch` 는 1.00 이다 — **모아 보낼 것이
없다.** 24절에서 게더 라이트(scatter-gather)가 준비돼 있는데도 실제로 묶이지 않는
이유가 이것이다.

**결국 43% 는 "호출 하나가 비싸서" 라기보다 "값싸게 만들 수 없는 호출을 초당 11,500번
해서" 다.** 11,500 x 8.4us = 97 ms/s 는 이 구조에서 바닥이고, 나머지는 그 위에 붙는다.

### 줄이는 길은 둘뿐이고, 둘 다 대가가 있다

- **호출 수를 줄인다** = 송신 주기를 낮춘다 = 동기화 품질(24절에서 이미 결론). 세션당
  틱 한 통이라 품질을 건드리지 않고 묶을 방법이 없다.
- **호출당 비용을 줄인다** = 8.4us 바닥값을 건드려야 한다. 이 값의 상당 부분은 WFP
  필터 계층으로 보이는데(소켓 수·바이트와 무관한 고정 비용이 그 특징이다), 서버
  코드로 어쩔 수 있는 것이 아니다. 운영 환경에서 인바운드/아웃바운드 필터 규칙과
  실시간 검사 예외를 손보는 쪽이다.

그래서 **27절의 결론이 그대로 유지된다** — 품질 손실 없이 줄일 수 있는 것은 선형 항인
`async_write` 가 아니라 제곱 항인 직렬화(그리드 조각 공유)다.

### 재지 않은 것

**실제 NIC 로 나가는 경우는 재지 않았다.** 기계 밖 주소로 UDP 를 쏘면 잴 수 있지만
사용자의 로컬 네트워크에 수십 MB 의 실제 트래픽을 얹게 되어 하지 않았다. 위의
8.4us 는 UDP 루프백 값이므로 여기에도 피어 소켓 전달이 일부 섞여 있다 — 즉
**"TCP 몫은 2.3us 이하" 는 확실하고, "소켓 계층 몫이 정확히 8.4us" 는 상한이다.**

벤치마크 소스는 저장소에 두지 않았다(측정용 일회성). 다시 만들려면 위 '재는 법' 대로
IOCP + `OVERLAPPED` + `WSABUF` 2개로 `WSASend` 를 걸고 제출 시각만 재면 된다.

## 29. 검토 기록 — `DoWrite` 를 별도 스레드로 빼면?

구현하지 않았다. **검토만 하고 순서를 뒤로 미룬 기록이다.**

27절에서 `async_write` 가 프레임의 43%(285 ms/s)를 차지하고 그것이 월드 스레드 안에서
동기적으로 일어난다는 것이 나왔다. 그러면 자연히 떠오르는 수가 하나 있다 —
`GameSession::DoWrite` 를 다른 스레드로 넘기면 월드 틱이 그만큼 가벼워지지 않는가.

### 먼저 — 순진한 버전은 아무것도 사지 않는다

```cpp
boost::asio::post(socket_.get_executor(), [self]{ self->DoWrite(); });
```

이것은 **같은 워커 스레드**로 미루는 것이다. 그 io_context 를 `poll()` 하는 것이
바로 그 스레드이기 때문이다(`IoWorker::PollIo`). `sim` 에서 `frame` 으로 계정만 옮겨
가고 벽시계는 그대로다. 285 ms/s 는 여전히 같은 코어가 낸다.

### 진짜로 빼려면 이 설계의 전제를 건드려야 한다

`Server.h` 의 `IoWorker` 주석이 전제를 그대로 적어 두고 있다.

> io_context마다 정확히 하나의 스레드만 돌리므로, 해당 io_context에 속한 서버/세션의
> 핸들러와 게임 로직은 서로 동시에 실행되지 않는다. (스레드 간 게임 상태 공유가 없어
> 락 없이 안전하다.)

io_context 에 스레드를 더 붙이면 **읽기 완료도 그 스레드들로 간다.**
`GameSession::HandlePacket` -> `PlayerController::handle` 이 월드를 직접 변경하므로,
그 순간 월드가 멀티스레드가 된다.

**strand 로도 막을 수 없다.** `UpdateGameLogic` 은 io_context 를 거치지 않고
`ServerManager::RunWorker` 에서 직접 호출된다. strand 는 핸들러끼리만 직렬화하지
io_context 밖의 코드와는 묶을 수 없다. 지금 안전한 것은 순전히 "같은 스레드가
`poll()` 한 뒤에 `UpdateGameLogic()` 한다" 는 순서 때문이다.

### 실현 가능한 형태 (asio 를 쓰지 않는 쪽)

변경을 송신 경로 안에 가두는 설계는 있다.

```
Send (월드 스레드)   : 세션 뮤텍스 -> writeMsgs_ push -> '쓸 것 있음' 을 MPSC 큐에 push
                       25us -> 약 0.1us
송신 스레드          : 큐에서 꺼내 writeBuffers_ 구성 후 async_write 제출
OnWrite (워커 스레드) : 같은 뮤텍스로 완료 처리, 남아 있으면 다시 큐에
```

읽기와 월드 로직은 그대로 둘 수 있다. **단, 명확한 위험이 하나 남는다** —
`DisconnectDeferred` 가 워커 스레드에서 `socket_.close()` 를 부르는데 송신 스레드가
`async_write` 중일 수 있다. asio 소켓은 읽기/쓰기 동시는 견디지만 close 동시는 아니다.
뮤텍스가 close 까지 덮어야 한다.

### 그런데 효과가 기대만큼 크지 않다 — 제곱 항이 곧 자리를 채운다

27절의 항별 지수로 한 워커의 한계선을 풀었다(1,000명 기준값 x N 배율).

```
write 285 x^1.1 + 직렬화 199 x^2.4 + PollIo 112 x^0.5 + sys 42 x^2.2 + 기타 12 x
```

| | 1,000명 월드 스레드 | 한계선 | 대가 |
|---|---|---|---|
| **현재** | 667 ms/s | ~1,320명 | — |
| **`DoWrite` 오프로딩** | ~410 ms/s | **~1,650명** (+25%) | 동시성 도입, close 경합 |
| **그리드 조각 공유** | ~430 ms/s | **~2,400명** (+82%) | 없음(단일 스레드 재구성) |
| 둘 다 | ~170 ms/s | 3,000명 이상* | |

\* 이 지점에서는 26절의 이벤트 팬아웃처럼 이 모델에 없는 항이 먼저 나타나므로 외삽이
의미를 잃는다. 그리고 위 값들은 27절 A 회차(느린 쪽) 기준이라 ±25% 폭을 갖는다.

오프로딩이 덜 버는 이유는 분명하다. **선형 항(write)을 치우면 제곱 항(직렬화 N^2.4)이
바로 그 자리를 채운다.** 1,650명 근처에서 직렬화 혼자 예산을 다 쓴다. 반대로 조각
공유는 제곱 항 자체를 없애므로 남는 것이 선형 항뿐이라 훨씬 멀리 간다.

### 그리고 짚어야 할 전제 — 기계 수용량은 늘지 않는다

오프로딩은 285 ms/s 를 **다른 코어가 내게 할 뿐** 기계 전체 CPU 를 줄이지 않는다.
지금 스케일 모델은 `포트 N개 = 월드 N개 = 스레드 N개`(`ResolveWorkerCount`)라
16코어를 이미 월드 16개로 쓸 수 있다.

**오프로딩이 사는 것은 "월드 하나에 더 많이 담기" 이지 "기계 전체 수용량" 이 아니다.**
후자가 목표라면 이득이 0이다.

### 결론 — 조각 공유가 먼저, 오프로딩이 두 번째

순서를 이렇게 두는 이유가 하나 더 있다. **조각 공유를 하고 나면 write 가 유일하게
남는 항이 되어서, 그때는 오프로딩이 애매한 최적화가 아니라 명백히 맞는 다음 수가
된다.** 지금 하면 동시성을 들여오고도 같은 벽에 막힌다.

조각 공유를 시작하려면 24절의 제약부터 풀어야 한다 — FlatBuffers 테이블은 상대 오프셋과
vtable 때문에 바이트로 이어붙일 수 없으므로, 셀 조각을 공유하려면 고정 크기 구조체
포맷을 먼저 설계해야 한다.

> **이 절의 결론은 30절에서 뒤집혔다.** 여기서 검토한 것은 `DoWrite` 하나만 빼는 좁은
> 안이었고, **송신 단계 전체를 병렬화하는 안은 값이 다르다.**

## 30. 검토 기록 — `SendPendingViews` 전체를 병렬로

29절은 `DoWrite` 하나만 다른 스레드로 빼는 안을 검토하고 "+25% 뿐이니 뒤로" 라고
결론지었다. **그 검토가 좁았다.** 빼야 할 것은 write 하나가 아니라 **송신 단계 전체**다.

```
[phase] 합계 538 ms/s | ... SEND 489 (acq 1  ser 199  wr 285)
```

`SendPendingViews` 를 통째로 병렬화하면 write(285) 만이 아니라 **직렬화(199)까지 같이
나뉜다. sim 의 91% 다.** 29절이 다룬 것은 그중 절반이었다.

### 커널이 직렬화하지 않는다 — 이것부터 쟀다

병렬화의 전제는 "여러 스레드가 동시에 `WSASend` 를 걸면 실제로 병렬로 나가는가" 다.
28절에서 잰 8.4us 바닥값이 커널 락 뒤에 있다면 write 는 하나도 안 줄고 직렬화만 준다.
28절의 마이크로벤치에 송신 스레드 수를 넣어 쟀다(1,000 소켓, 1300B).

| 송신 스레드 | us / 호출 | 배속 |
|---|---|---|
| 1 | 11.75 | 1.00x |
| 2 | 6.38 | **1.84x** |
| 4 | 4.49 | **2.62x** |

**직렬화하지 않는다.** 완전 선형은 아니지만(4스레드 2.62x) 실질적이고, 이 수치는
라운드마다 스레드를 새로 만드는 오버헤드를 포함하므로 실제로는 조금 더 좋다.
(8스레드는 반복 실행으로 임시 포트가 말라 안정적으로 재지 못했다.)

### 막는 것이 생각보다 적다

`SendPendingViews` 의 슬롯 루프는 슬롯끼리 독립적이다. 코드를 훑어 확인한 것들:

| | 상태 |
|---|---|
| `Actor::GetActorInfo` | **순수하다.** position/state/health/isInputLocked 를 읽고 빌더에만 쓴다 |
| 액터가 이 구간에 변하는가 | **안 변한다.** `UpdateGameLogic` 중에는 `PollIo` 가 돌지 않아 핸들러가 없다 |
| `players_` 가 변하는가 | **안 변한다.** 21절 이후 `DisconnectDeferred` 가 `leave` 를 io_context 로 미룬다 |
| `BroadcastScope` | 이미 루프 **밖**에 있다(`broadcastDepth_` 경합 없음) |
| `SendMessagePool` | **thread_local 이고, 회수 조건이 `use_count()==1` + acquire 펜스다.** 다른 스레드가 반납해도 성립하도록 이미 그렇게 설계돼 있다 |
| `writeMsgs_` | 슬롯 1개 = 플레이어 1명 = 세션 1개라 **쓰는 스레드가 정확히 하나**다 |
| `OnWrite` 동시 실행 | 없다. 이 구간에 `PollIo` 가 돌지 않는다 |

고쳐야 하는 것:

- **`aoi_->infoScratch`** — 맵이 하나 들고 쓰는 공용 스크래치다. 스레드별로 나눠야 한다.
- **`g_sendCounters`** — `thread_local` 이라 병렬 스레드가 각자 쌓고, `[tick]` 은 워커
  스레드 것만 읽는다. **계측이 조용히 축소 집계된다.** 합산이 필요하다.
- **`ServerConfig::Instance().Network()`** — 슬롯마다 읽는다. 런타임에 안 바뀌는 것이
  확실한지 확인해야 한다.
- **DB 스레드풀** — `Player::GetStrand()` 가 `thread_pool` 위의 strand 다. DB 완료가
  플레이어 상태를 건드린다면 그것은 **오늘도 이미** 월드 스레드와 동시에 도는 것이라
  이 변경이 새로 만드는 위험은 아니지만, 착수 전에 확인해 둘 항목이다.

### 값

4스레드(2.62x) 기준으로 27절의 항에 넣으면

```
(285 x^1.1 + 199 x^2.4) / 2.62  +  112 x^0.5  +  42 x^2.2  +  12 x
```

| | 1,000명 월드 스레드 | 한계선 |
|---|---|---|
| 현재 | 667 ms/s | ~1,320명 |
| `DoWrite` 만 오프로딩(29절) | ~410 ms/s | ~1,650명 (+25%) |
| **송신 단계 전체 병렬(4스레드)** | **~350 ms/s** | **~2,000명 (+51%)** |
| 그리드 조각 공유 | ~430 ms/s | ~2,400명 (+82%) |
| 조각 공유 + 병렬 | ~150 ms/s | 3,000명 이상* |

\* 이 지점에서는 26절의 이벤트 팬아웃처럼 모델에 없는 항이 먼저 나타난다.

**틱 점유는 지금 당장 절반 이하로 떨어진다** — sim 538 -> 약 240 ms/s. 한계선 증가폭
(+51%)보다 이쪽이 더 크게 체감되는 변화다.

### 그래서 순서를 바꾼다 — 병렬화가 먼저다

29절에서 "조각 공유 먼저" 라고 한 것은 **한계선 증가폭만 보고 구현 비용을 달지
않았기 때문**이다. 둘을 나란히 놓으면:

| | 한계선 | 구현 범위 | 위험 |
|---|---|---|---|
| 송신 단계 병렬 | +51% | 함수 하나 + 스크래치/계측 3건 | 동시성 버그(부하에서만 드러남) |
| 조각 공유 | +82% | **새 와이어 포맷 + 클라 변경 + 조각 캐시 + 인플라이트 refcount** | 프로토콜 호환 |

**병렬화가 훨씬 싸게 붙고, 지금 당장의 틱 점유를 더 크게 줄인다.** 조각 공유는
`enters`/`leaves` 를 여전히 뷰어별로 남겨야 하고 Unity 클라의 파서까지 건드려야 한다.

그리고 **둘은 경쟁 관계가 아니다.** 조각 공유는 *할 일의 양*을 줄이고, 병렬화는
*남은 일*을 나눈다. 조각 공유를 나중에 해도 write(285)는 줄지 않으므로 병렬 구간은
계속 값을 한다.

### 주의 — 기계 전체 수용량은 여전히 안 늘어난다

29절과 같은 단서가 그대로 붙는다. 489 ms/s 를 다른 코어가 낼 뿐 총 CPU 는 같다.
지금 스케일 모델이 `포트 N개 = 월드 N개 = 스레드 N개` 라, 월드마다 송신 스레드를
4개씩 띄우면 16월드에 64스레드가 필요해진다. **송신 풀은 월드끼리 공유해야 하고,
모든 월드가 10Hz 로 같이 틱하므로 송신 구간이 동시에 몰린다** — 풀 크기와 몰림을
같이 봐야 한다.

또 하나, **배리어 비용**이 있다. 월드 스레드는 가장 느린 조각을 기다린다. 뷰어당
entries 편차가 크므로(메시지당 176~242 는 평균이고 개별 편차는 더 크다) 정적 분할이
아니라 동적 분할이 필요하다.

> **31절에서 구현하고 실측했다.** sim 443 -> 162 ms/s, `over100` 4/688 -> 0/691.
> 배리어 걱정은 근거가 있었다 — 꼬리 지연(ping p99)이 119 -> 191ms 로 나빠졌다.

## 31. 조치 #15 — 송신 단계를 작업자 풀로 나눴다

30절의 검토대로 `Map::SendPendingViews` 를 병렬화했다. 검토가 아니라 구현과 실측이다.

### 무엇을 바꿨나

- **`ECS/ParallelFor.h`** — 프로세스에 하나뿐인 작업자 풀과 그 위의 `ParallelFor`.
  하위 계층(ECS)에 둔 것은 Engine 이 ECS 를 참조해서 시스템과 맵 양쪽에서 쓸 수 있기
  때문이고, 프로세스에 하나인 것은 월드마다 풀을 두면 월드 16개 x 4스레드 = 64스레드가
  되기 때문이다. **호출 스레드도 함께 일하므로 보조 스레드가 0개면 그대로 순차 실행**이다
  — Start() 를 부르지 않는 테스트/벤치마크는 예전과 완전히 같은 경로를 지난다.
- **`Map::SendPendingView(slotIndex, workerIndex)`** — 슬롯 하나 몫을 떼어냈다.
  `SendPendingViews` 는 보낼 슬롯만 추려 `sendList` 에 담고 그것을 나눈다.
- **스레드별 스크래치** — `infoScratch` 를 `workerIndex` 로 색인하는 배열로 바꿨다.
  하나를 공유하면 조립 중에 남의 `clear()` 를 맞는다(아래 회귀 테스트에서 실제로 죽는다).
- **계측 카운터를 서버별 원자 카운터로** — `thread_local SendCounters` 는 '워커 하나 =
  스레드 하나' 라는 전제 위에 있었다. 송신이 여러 스레드로 나뉘면서 그 전제가 깨져
  **조용히 축소 집계된다.** `GameServer::SendCounters` 로 옮기고 `IoWorker::TakeSendCounters()`
  가 워커 단위로 다시 합산한다.
- **`deferredLeaves_` 를 뮤텍스로** — 조립 중 퇴장이 여러 스레드에서 겹쳐 들어올 수 있다.
  `broadcastDepth_` 는 원자로 바꿨다. leave 는 드문 경로라 값이 싸다.
- **`world.send_threads` 설정** — 0 이면 자동(코어 수에 맞춰 0~3), 음수면 끔.

`ServerConfig` 는 기동 시 한 번 로드되고 그 뒤 읽기 전용이라, 슬롯마다 읽는
`Network().max_send_queue` 는 그대로 두어도 안전하다(30절의 확인 항목 중 하나였다).

### 인접 A/B — 같은 바이너리로 설정만 바꿔 연달아 돌렸다

1,000명, 맵 1, 반경 10, 새 계정(뭉친 시작). 27절에서 실행 간 편차가 ±25% 라는 것이
나왔으므로 두 구성을 연달아 돌렸다.

| | sim ms/s | frame ms/s | SEND | sys | over100 | write/s | entries/s |
|---|---|---|---|---|---|---|---|
| 병렬 끔 | 443 | 560 | 381 | 41 | **4/688** | 11,658 | 2,395,053 |
| **병렬 켬(보조 3 + 호출자)** | **162** | **290** | **110** | 38 | **0/691** | 11,600 | 2,226,366 |

**`write/s` 와 `entries/s` 가 거의 같다 — 같은 일을 했다는 뜻이다.** 그 위에서

- **sim 443 -> 162 ms/s (2.7배)**
- **SEND 381 -> 110 ms/s (3.5배)**
- **frame 560 -> 290 ms/s (1.9배)**
- **`over100` 4/688 -> 0/691**
- `sys` 는 41 -> 38 로 그대로다. 직렬 구간은 손대지 않았으니 당연하고, **이것이
  측정이 제대로 됐다는 방증이기도 하다**(병렬로 바꾼 항만 줄었다).

30절에서 예측한 것은 '월드 스레드 ~350 ms/s' 였는데 실측이 290 이다. 예측보다 낫다 —
직렬화는 순수 CPU라 거의 선형으로 나뉘고, `WSASend` 만 28절의 2.62배에 묶인다.

### 병목이 옮겨 갔다

이제 프레임 290 ms/s 의 내역은 이렇다.

| 구간 | ms/s | 프레임 대비 |
|---|---|---|
| **완료 핸들러(PollIo)** | **128** | **44%** |
| SEND(병렬) | 110 | 38% |
| `UpdateSystems` | 38 | 13% |
| 나머지 월드 로직 | ~14 | 5% |

**가장 큰 항이 이제 `PollIo` 다.** 27절에서 17% 였던 것이 다른 항이 줄면서 44% 가 됐다.
`OnWrite` 완료(초당 11,600개)와 수신 처리가 거기 있다. 다음에 볼 곳은 여기다.

### 대가 — 꼬리 지연은 조금 나빠졌다

| Ping | p50 | p95 | p99 | max |
|---|---|---|---|---|
| 병렬 끔 | 17 | 47 | **119** | **366** ms |
| 병렬 켬 | 16 | 38 | **191** | **461** ms |

**전형적인 경우(p50/p95)는 좋아졌는데 꼬리(p99/max)는 나빠졌다.** 배리어 때문으로
보인다 — 월드 스레드가 가장 느린 청크를 기다리므로, 한 조각이 밀리면 틱 전체가 밀린다.
청크 크기(`kSendChunk = 16`)와 몰림을 더 볼 여지가 있다. 끊긴 세션은 양쪽 모두 0이다.

### 회귀 테스트가 실제로 잡는지 확인했다

`ParallelSendReachesEveryViewer` 와 `ParallelSendSurvivesPlayersLeavingDuringSend` 를
넣었다. 풀은 프로세스 전역이라 이 두 테스트에서만 RAII 로 켠다.

**스크래치를 다시 하나로 공유하도록 되돌려 보니 접근 위반(0xc0000005)으로 죽는다.**
21절에서 배운 대로, 잡지 못하는 회귀 테스트는 없느니만 못하므로 확인하고 넘어갔다.

Release 495 / Debug 495 전부 통과, 경고 0.

### ECS 는 손대지 않았다 — 필요한 곳이 없었다

같이 검토했지만 바꾸지 않았다.

- `SendPendingViews` 는 **엔티티가 아니라 뷰어 슬롯을 순회한다.** 시스템으로 만들면
  모양만 ECS 고 실제로는 맞지 않는다.
- 남은 단계(`UpdatePlayerDeath`, `UpdateGameMode`, `UpdateMonsterSpawns`)는 22절에서
  이미 본 대로 Lua/부활 타이머/스포너라 ECS 형태가 아니고, 다 합쳐 프레임의 5% 다.
- `UpdateSystems`(38 ms/s) 안의 `SyncActorState` 는 제곱으로 자라는 항이 맞지만,
  `QueueUpdate` 가 **셀 구독자 전원의 대기열에 밀어 넣는** 구조라 슬롯끼리 독립적이지
  않다. 스레드별 버퍼로 모았다가 합치는 방법이 있는데 합치는 비용이 그대로라 지금은
  값이 없다.

대신 **`ParallelFor` 를 ECS 계층에 두어 `SystemManager` 가 나중에 쓸 수 있게** 했다.
지금 그것을 필요로 하는 시스템이 없어서 API 는 추가하지 않았다 — 쓰지 않는 API 를
미리 만들면 그것이 곧 유지 비용이다.

## 32. 육안 확인 — 그리고 Debug 빌드로 하루를 태울 뻔한 이야기

23절과 25절이 "눈으로 보고 정할 값" 으로 남겨 둔 항목들이 있었다. 봇으로는 볼 수 없는
것들이라 계속 열려 있었는데, 실제 클라이언트로 확인했다.

### 구성

```
서버   x64\Release\Game.exe 65001 --config ...   (송신 보조 스레드 3개)
봇     1,000명, 맵 1, 관심영역 켜짐(반경 10)
클라   유니티 에디터 1대가 같은 월드에 접속 (sess=1001)
```

```
frame avg 5.65~7.66 ms (35~38 fps) | sim avg 15.0~20.4 ms
over100 0/50 | late 0 | drop 0 | write ~11,000/s
[phase] 합계 179~199 ms/s | sys 36~41 | SEND 137~152 | viewers 10,000/s
경고 0, 에러 0
```

### 닫은 항목

- **거리별 갱신 빈도(23절)가 눈에 거슬리지 않는다.** 반경 10에서 2셀 밖은 3.3Hz,
  그 밖은 2Hz 로 솎이는데, 1,000명이 붙은 상태에서 이동이 부드럽게 보인다.
  클라의 등속 보간(`Actor.InterpolatedPosition`)이 그 간격을 메운다.
- **위치 잔차가 보이지 않는다.** 23·25절이 남겨 둔 것 — 먼 액터가 솎이는 틱에 멈추면
  마지막 이동분(최대 ~1.8유닛)이 전달되지 않는 문제다. `StateComponent` 를 12 -> 16바이트로
  키워야 상한을 둘 수 있어 미뤄 뒀는데, **실제로 보이지 않으므로 그대로 둔다.**
- **반경 10 이 시야로 충분하다(25절).** 몬스터 탐지 반경과 같은 값이라 "몬스터가 나를
  인지하는 순간 화면에 있다" 가 성립한다.
- **병렬 송신(31절)에 눈에 띄는 산출물이 없다.** 배리어 때문에 꼬리 지연이 나빠지는
  것은 측정에 남아 있지만, 사람 눈으로는 드러나지 않았다.

### 그런데 그 전에 하루를 태울 뻔했다 — Debug 빌드

같은 구성인데 이동이 심하게 끊겨서 원인을 찾았다. 로그는 이랬다.

```
sim avg 713 ~ 1,377 ms   (예산 100ms)
over100 4/4, 5/5, 6/6    ← 모든 sim 프레임이 예산 초과
late 4~6, drop 4~6       ← 따라잡기 상한을 넘겨 틱을 버림
write 2,451/s            ← 정상은 11,000/s
```

월드가 초당 3.9회만 돌았으니 클라가 끊겨 보이는 것이 당연했다. **원인은 서버가
Debug 빌드였던 것뿐이다.** Release 로 바꾸니 그대로 정상이 됐다.

| | Debug | Release |
|---|---|---|
| sim avg | 713~1,377 ms | **15~20 ms** |
| over100 / drop | 4/4~6/6 / 4~6 | **0/50 / 0** |
| write/s | 2,451 | **11,000** |
| `sys` | 304 ms/s | **38** |
| `SEND` | 536 ms/s | **145** |

**70배다.** MSVC Debug 는 `_ITERATOR_DEBUG_LEVEL=2` 로 검사된 이터레이터를 쓰는데,
송신 경로가 전부 `std::vector` / `std::deque` / `shared_ptr` 연산이라 정확히 거기서
가장 비싸진다.

**진단이 한 번 헛짚었다.** "관심영역이 켜지기 전 브로드캐스트 구간에서 이미 2배 느리다"
까지는 맞게 봤는데, 원인을 같은 기계에서 도는 유니티 에디터와의 CPU 경합으로 결론지었다.
Debug 가 그 2배도 설명한다.

되짚어 보면 **더 앞에서 잡을 수 있었다.** 클라 1대만 붙은 로그에서 `sim avg 3.0~3.9 ms`
를 보고 정상이라고 넘겼는데, 같은 조건의 Release 는 **0.54 ms** 다. 6~7배 차이를
그냥 지나갔다.

**그래서 기동 로그에 빌드 구성을 남긴다.** 한 줄이면 이 진단이 1분에 끝났다.
`[tick]` 수치를 이 문서의 표와 비교할 때 첫 번째로 확인해야 하는 값이기도 하다.
