## B. 대화

### B1. 클라이언트 대화 UI

- [x] **B1-1.** 대화 창과 그 앞뒤 배관을 붙였다. 서버가 보낸 노드를 그리고, 고른 번호를
      그대로 돌려보낸다.

      | 파일 | 역할 |
      | --- | --- |
      | `Scripts/UI/DialogWindow.cs` | 창(코드로 만든다 — 프리팹/씬 배치 없음) |
      | `Scripts/Dialog/DialogController.cs` | 상호작용 → 노드 표시 → 선택 회신. Session 의 역할 객체 |
      | `Scripts/PacketFactory.cs` | `CreateInteractMessage` / `CreateDialogSelectMessage` |
      | `Scripts/Session.cs` | `DialogNode` 수신 분기, `Interact()`, 가장 가까운 NPC 에게 말 걸기 |
      | `Scripts/GameData/ResourceLoader.Localization.cs` | text_id → 문장 (새로 붙임) |

      **창을 씬이 아니라 코드로 만든다.** 대화는 어느 맵에서나 필요한데 게이트로 씬이
      바뀌므로, 씬에 배치하면 네 개 씬에 같은 것을 두고 계속 맞춰야 한다.
      `DamageTextManager` 와 같은 방식으로 처음 필요할 때 만들고 씬 전환에도 유지한다.

      **로컬라이즈 표가 클라에 없었다.** 데이터는 `text_id` 만 담고 문장은 로컬라이즈
      파일에 있는데, 클라가 그 파일을 읽는 코드가 없어 창을 붙여도 `dlg_rinne_greet` 이
      그대로 보일 상황이었다. 표는 `{ "키": "문장" }` 평평한 객체라 테이블 로더(생성 코드)를
      타지 않으므로 손으로 쓰는 쪽(`ResourceLoader.Localization.cs`)에 두었다.
      키가 없으면 키를 그대로 보여 준다 — 빈칸이면 "문장이 없다"와 "키가 틀렸다"를 구분할 수 없다.

      **NPC 를 누르는 대신 F 키로 말을 건다.** 씬에 NPC 오브젝트가 아직 없어 누를 대상이
      없다(A1-Unity 와 같은 문제다). `npc.json` 의 좌표로 지금 맵에서 상호작용 거리 안의
      가장 가까운 NPC 를 찾아 같은 `Interact` 를 보낸다 — 서버도 데이터 좌표로 거리를 재므로
      판정은 같다. 씬에 NPC 가 생기면 클릭에서 `Session.Interact(npcId)` 를 부르면 된다.

      컴파일은 확인했다(`Client/Assembly-CSharp.csproj` 빌드, 에러 0 / 새 파일 경고 0).
      화면에 실제로 어떻게 보이는지는 에디터에서 봐야 한다 → E4.

      오브젝트를 바꿔 그린다. 서버 구조를 안 건드린다.
      진짜 페이징(같은 맵의 다른 인스턴스)은 4막 전장부터 필요하다.

### C4. 최종 선택을 담는 그릇

      자체를 기록할 자리가 없어 대화 선택지 → 퀘스트 수락으로 우회해야 한다.

## E. 확인 작업 (서버/클라 실행 필요)

> **봇으로 대신 볼 수 있게 됐다.** 부하 테스트 봇([Bot](../Bot))이 메인 퀘스트를 처음부터
> 진행한다 — 데이터를 읽어 NPC 를 찾아가고, 대화로 받고, 목표를 수행하고, 게이트로 맵을 옮긴다.
> 봇은 씬을 쓰지 않으므로 **A1-Unity 없이도 서버 쪽 진행은 전부 확인된다**.
> 사람이 눈으로 봐야 하는 것(연출·밀도 체감·UI)만 남는다.

- [x] **E1. 1막 전체 실플레이** — 봇 4명, 45분. 한 봇이 **11001 → 11008 을 끝까지 완주**했고
      다른 봇이 반대편 가지(11009)를 완주했다. 새로 뚫은 두 통로가 양방향으로 돌고,
      `reach 13`(11002)도 밭길 진입에서 제때 발동했다(11002 완료 222초).

      | 퀘스트 | 수락 → 완료 | 비고 |
      | --- | --- | --- |
      | 11001 | 54s / 132s | 슬라임 5 + 마을↔바람고개 왕복 |
      | 11002 (가지 A) | 222s | 늑대 8 + `reach 13` |
      | 11009 (가지 B) | 99s | 고블린 8 |
      | 11003 | 105s | 선택 보상 — `QuestComplete` 경로 |
      | 11004 | 127s | 밭길→잿빛 숲(게이트 1008) + 카일 + 오크 6 |
      | 11005 | 159s | 다크 엘프 8 + 일지(드롭 0.5) |
      | 11006 | 434s | 해골 10 + 시체 8 |
      | 11007 | 578s | 망령 5 + 두목(단독 스폰, 재생성 60초) |
      | 11008 | 152s | 골렘 + 탁본(드롭 1.0) |
      | 1001 (체인 10) | 739s | 레벨 3까지 올린 뒤 고블린 10 + 귀 5 + 마을 귀환 |

      **봇 쪽 결함을 둘 잡았다.** 둘 다 데이터가 아니라 봇 로직 문제이고, 증상은 똑같이
      "그 봇만 조용히 아무것도 안 한다"였다.

      1. 레벨이 모자라 수락 선택지가 안 보이는 동안 **시도 횟수**로 포기를 판단해, 레벨을
         올리는 데 오래 걸린 봇이 1001 을 포기하고 그 뒤 체인 전체가 선행 미달로 막혔다.
         포기 기준을 '얼마나 오래 안 열렸는가(10분)'로 바꾸고, 건너뛴 퀘스트를 이유와 함께
         로그로 남기게 했다(회귀 테스트 `DoesNotGiveUpOnAQuestThatMayOpenLater`).
      2. 그 로그가 바로 두 번째를 드러냈다 — **가지 B 를 탄 봇이 합류 지점에서 막혔다.**
         리네의 첫 노드에는 3203(11003 을 주는 곳)으로 가는 길이 둘 있고 각각 "11002 완료"와
         "11009 완료"에 걸려 있는데, 봇이 길을 **하나만** 찾아 그것이 닫혀 있으면 포기했다.
         목적지에 닿는 길을 전부 모아 그중 서버가 실제로 보낸 것을 고르게 고쳤다
         (회귀 테스트 `FindsEveryRouteToAQuestActionNotJustTheFirst`,
         `TakesTheOpenRouteWhenTheOtherBranchesRouteIsClosed`).

      분기를 데이터에 넣을 때 **합류 지점의 길도 가지마다 하나씩** 있어야 한다는 뜻이기도 하다
      (`show_if` 는 퀘스트 하나만 묻기 때문에 "둘 중 하나"를 한 선택지로 적을 수 없다).

- [x] **E2. 잿빛 숲 스폰 밀도 체감** — 목표가 막히는 구간은 없었다. 다만 **11006(해골 10 +
      시체 8, 434초)과 11007(망령 5 + 두목, 578초)이 다른 칸의 3~5배**로 길다.
      11007 은 두목이 단독 스폰 + 재생성 60초라 기다리는 시간이 그대로 얹힌다.
      마커를 늘리기보다 **요구 수량을 줄이는 편**이 자연스러워 보인다(디자인 판단이라 남겨 둔다).

- [x] **E3. 퀘스트 아이템 드롭률 체감** — 수집 목표가 처치 목표보다 오래 걸리는 구간은 없었다.
      11003(고블린 10 + 화물표 3, 드롭 0.6)은 105초로 오히려 짧은 편이고,
      11005(일지 0.5), 11008(탁본 1.0)도 같은 스테이지의 처치 목표 안에서 함께 채워졌다.
      드롭률은 지금 값이 맞다.
- [ ] **E4. 조건부 선택지 육안 확인** — B1(클라 UI)이 나온 뒤에야 가능하다.
      그전까지는 `UnitTest.exe --gtest_filter=*Dialog*` 가 유일한 확인 수단이다.
- [ ] **E5. 잿빛 숲 난이도** — 오크(lv5)부터 골렘(lv12)까지 한 맵에 섞여 있다.
      lv5 플레이어가 골렘 구역(−18, 18)에 실수로 들어가 죽는 일이 잦으면 마커를 더 벌린다.
      봇 실플레이에서는 **퀘스트 순서대로 가면 레벨이 따라붙어** 막히지 않았다(11008 까지 완주).
      다만 봇은 목표 몬스터의 스폰 지점으로 곧장 가므로 "실수로 들어가는" 경우는 재현되지 않는다.
